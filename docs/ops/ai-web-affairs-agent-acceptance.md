# AI 网页事务代理人验收手册

> 当前范围：W1“网站与账号闭环”
> 当前状态：自动化通过，真人验收待执行
> 管理事实源：`docs/features/ai-web-affairs-agent-development-plan.md`

> 2026-07-31 决策：用户明确批准本次真人登录验收延期，以继续开发不产生网页外部副作用
> 的 A1 手工事务能力。该决定不代表本验收通过；A2 真实网页执行前必须补测。

## 1. 验收目标

证明用户可以把未预置网站和两个真实测试账号纳入“网站与账号”，用不同 Browser
Profile 手动登录，重启 Studio 后保持正确登录态，且两个账号不会串用。此验收不执行
发布、付款、提交审核或其他不可逆业务动作。

## 2. 前置条件

- 选择一个允许此类测试、风险可控且不会触发真实业务提交的网站。
- 准备两个可区分的测试账号；不要使用唯一管理员或高权限生产账号。
- 为两个账号准备不同且可识别的 Browser Profile 名称。
- 验收人员能够完成验证码、扫码、2FA 和隐私授权等人工步骤。
- 如验证旧配置导入，使用一个可备份的真实旧项目，并先记录
  `cclink-accounts.json` 的 SHA-256。

## 3. W1 真人验收步骤

| #   | 用户动作                                        | 通过标准                                   | 结果   |
| --- | ----------------------------------------------- | ------------------------------------------ | ------ |
| 1   | 启动 Studio，点击 Activity Bar 的“网站与账号”   | 无预置平台限制，可看到“添加网站”           | 待验收 |
| 2   | 添加目标网站、主体 A、账号 A、Profile A         | 列表显示网站、主体、账号和 Profile A       | 待验收 |
| 3   | 打开账号 A 的资源详情并点击“打开网站”           | 浏览器使用 Profile A 打开正确办理入口      | 待验收 |
| 4   | 人工完成账号 A 登录，返回详情点击“核验登录”     | 显示最近核验时间和脱敏会话状态             | 待验收 |
| 5   | 添加同网站的账号 B，绑定不同的 Profile B 并登录 | 两份详情显示不同 Session Partition         | 待验收 |
| 6   | 分别打开账号 A、B，并在页面内核对当前账号身份   | A、B 各自正确，切换时不串号                | 待验收 |
| 7   | 完全退出并重启 Studio，再分别打开 A、B          | 两份资源存在；登录态和页面账号身份保持正确 | 待验收 |
| 8   | 在有旧配置的本地项目点击“导入旧配置”，指定主体  | 平台成为普通网站资源，Profile ID 保持不变  | 待验收 |
| 9   | 再次执行同一导入                                | 新增 0 个，已有账号全部跳过                | 待验收 |
| 10  | 比较旧配置导入前后的 SHA-256                    | `cclink-accounts.json` 未变化且未被删除    | 待验收 |

## 4. 失败时记录

每个失败至少记录：步骤编号、时间、网站 URL、账号标签、Browser Profile、资源详情中
显示的 Session Partition、页面实际账号身份、错误文案和截图。不得记录密码、完整
Cookie、验证码、2FA 恢复码或身份证件正文。

出现以下任一情况，W1 保持 `In Progress` 或退回 `In Progress`：

- 重启后资源或登录态丢失。
- 两个账号共用同一 Session Partition，或页面身份发生串用。
- 资源页把 Cookie 启发式误报为确定的页面账号身份。
- 导入覆盖、删除旧文件或修改既有 Browser Profile。
- 登录失败时没有明确的人工接入或重新登录路径。

## 5. 自动化证据

- `pnpm smoke:ui`：7/7，通过 UI 创建两个 Profile、打开资源详情、比较 Session
  Partition，并在 Electron 重启后验证资源恢复。
- `pnpm test`：190 个测试文件、1106 项测试通过。
- `pnpm verify`：通过 OSS、凭证、上下文操作、发布、格式、Lint、测试、类型检查和生产
  构建门禁。

自动化证据不能替代步骤 4、6、7 的真实网站和真实账号身份核对。
