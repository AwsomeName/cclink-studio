## 结论

定时任务是绑定工作空间的一级资源，与文件、会话、Browser、Terminal 一样，可以从
左侧管理并在 Workbench 中打开。它不是设置页里的 Cron 表单，也不是藏在 Agent
会话中的一条提示词。

用户通过 Activity Bar 的“定时任务”按钮进入当前工作空间的定时任务侧栏；点击任务
后，在 Workbench 打开同一个定时任务 Tab。任务到点后由本地 Agent 执行，运行状态、
历史和产物回到该 Tab。关闭 Tab 不会暂停任务，切换工作空间也不会隐式终止任务。

第一版只承诺 CCLink Studio 运行期间的本地调度。应用完全退出后不会伪装成仍能准时
执行；错过的任务在下次启动时按明确的补执行策略处理。发布、发送、删除、支付等
不可逆外部动作仍必须由用户逐次确认。

第一版调度器只存在于 CCLink Studio 主进程，随 App runtime 启动和停止。不得注册
macOS LaunchAgent、Windows Task Scheduler、Linux cron/systemd timer、登录启动项、
后台 Helper、守护进程或其他操作系统级调度入口，不唤醒已退出的 App，也不在退出后
遗留子进程。最小产品闭环只覆盖定时读取工作空间资料并生成 Markdown 产物。

## 已确认的首版决策

| 决策         | 首版结论                                                     |
| ------------ | ------------------------------------------------------------ |
| 产品入口     | 独立 Activity Bar 按钮、当前工作空间侧栏、独立定时任务 Tab   |
| 资源归属     | 每个定时任务严格绑定一个本地工作空间                         |
| 调度所有者   | 当前 CCLink Studio 主进程内的 `ScheduledTaskService`         |
| 系统集成     | 不注册系统计划任务、后台服务、登录项或常驻 Helper            |
| App 退出     | 停止调度；运行中实例有界收束，未完成则中断，待触发项下次对账 |
| 定义存储     | 工作空间 `.cclink-studio/scheduled-tasks/`                   |
| 本机状态     | `userData/scheduled-tasks/` 保存启用、运行和权限事实         |
| 保存语义     | 显式保存；每次保存形成 revision，运行固定使用已保存 revision |
| 等待确认     | 当前运行结束为“需要处理”，用户确认后创建关联的新运行         |
| 首个产品闭环 | 到点读取工作空间文件、生成 Markdown、展示历史并打开产物      |

## 产品目标与端到端验收

产品目标必须通过以下真人操作验收：

1. 用户打开一个可写的本地工作空间。
2. 点击左侧 Activity Bar 的“定时任务”时钟按钮。
3. 侧栏只展示当前工作空间的定时任务，并提供“新建定时任务”。
4. 用户点击新建，Workbench 打开一个未保存的定时任务 Tab。
5. 用户填写名称、任务内容、执行时间、绑定资源和输出位置。
6. 用户点击“保存并在此设备启用”，Tab 清除未保存状态，侧栏显示下次运行时间。
7. 用户可以点击“立即运行”，并在同一个 Tab 看到运行步骤、结果和产物。
8. 到达计划时间后，任务在 Studio 运行期间自动开始；用户不需要停留在该 Tab。
9. 用户切换到另一个工作空间时，原任务继续运行，但不会混入新工作空间侧栏。
10. 任务完成、失败或需要处理时，Activity Bar 出现徽标；用户点击通知后回到任务所属
    工作空间并打开原任务 Tab。
11. 用户关闭并重新打开 Studio 后，能够看到历史运行和明确的中断、错过或下次运行
    状态，不出现看不出任务是否执行过的空白状态。
12. 如果任务要求 Terminal、浏览器提交、删除或其他首版未开放能力，保存确认和运行记录
    会明确显示不支持，不会因 `auto` 权限模式直接执行。
13. 用户设置一个几分钟后执行的任务并在到点前退出 Studio；任务不会由操作系统或残留
    进程执行。重新启动 Studio 后，任务显示明确的“已错过”或补执行状态。

只有以上流程在真实应用中通过，才能声明首版定时任务产品闭环完成。仅有调度器、
Schema、测试或 mock 页面时，只能声明相应工程准备度通过。

## 非目标

第一版不做：

- 云端全天候调度。
- Studio 完全退出后的准时执行承诺。
- macOS LaunchAgent、Windows Task Scheduler、Linux cron/systemd timer。
- 登录项、后台 Helper、守护进程、系统唤醒和退出后的残留子进程。
- 任意脚本式 Cron 编辑器。
- 无人值守自动发帖、评论、私信、删除、购买或支付。
- 多账号批量营销和平台任务市场。
- 把每次运行自动创建成新的会话或 Workbench Tab。
- 从工作空间文件自动继承本机权限或静默启用任务。
- 把官方账号、消息网络、网络 runtime、订阅或配额带入 OSS 默认路径。

## 用户心智与资源模型

产品文案统一使用“工作空间”。定时任务严格归属于一个 `WorkspaceRef`：

```text
Workspace
└── ScheduledTask
    ├── definition
    ├── localActivation
    ├── currentRun
    └── runHistory
```

用户只需要理解两个概念：

| 概念     | 用户含义                                             |
| -------- | ---------------------------------------------------- |
| 定时任务 | 保存好的任务内容、时间、资源和输出约定               |
| 一次运行 | 该定时任务在某个计划时间或“立即运行”操作下的实际执行 |

工程上可以使用 `ScheduledTask` 和 `ScheduledTaskRun`，但 UI 不展示内部 runtime、
conversation 或 scheduler 名称。

定时任务不是 Agent Thread。执行时可以使用内部 Agent 会话，但侧栏、Tab、状态和历史
都以定时任务为主资源。失败或需要继续沟通时，可以从某次运行点击“在 Agent 中继续”，
把任务、运行记录和产物作为资源挂载到一个工作空间会话。

### Activity Bar

Activity Bar 增加独立的“定时任务”时钟按钮，不放入“运营”侧栏。

原因是定时任务可以编排文件、Agent、浏览器、数据源、Terminal 和 Android，它不是
运营专属能力。

图标徽标规则：

| 徽标     | 含义                             |
| -------- | -------------------------------- |
| 蓝色数字 | 正在运行的任务数量               |
| 黄色数字 | 等待确认或需要用户处理的任务数量 |
| 红色数字 | 最近新增且尚未查看的失败数量     |

多个状态同时存在时，优先显示需要处理和失败；悬停信息列出各状态数量。徽标不能只根据
当前工作空间 renderer store 猜测，必须来自主进程运行事实。

Activity Bar 徽标统计所有已知工作空间的运行、失败和待处理状态；侧栏仍然只展示当前
工作空间。其他工作空间存在待处理项时，侧栏底部显示“其他工作空间还有 N 项需要
处理”，只有用户点击后才切换工作空间。

### 定时任务侧栏

侧栏只显示当前工作空间的定时任务：

```text
定时任务                                      ＋

需要处理
  ● 公众号草稿准备
    等待登录 · 10:03

正在运行
  ● 每周工作总结
    正在读取工作空间资料

已启用
  ○ 数据源日报
    下次：明天 09:00

已暂停
  ‖ 竞品信息整理
```

默认分组顺序：

1. 需要处理。
2. 正在运行。
3. 已启用。
4. 已暂停。

每行至少展示名称、状态和下次运行时间或当前步骤。失败项展示一行脱敏错误摘要，不在
侧栏铺开完整日志。

侧栏顶部提供：

- 新建定时任务。
- 搜索。
- 状态筛选。

点击任务打开同一个定时任务 Tab。侧栏上下文操作必须接入统一 Context Action System，
不能新增独立右键菜单实现。

### 定时任务 Tab

定时任务使用独立 Workbench Tab 类型。一个任务只对应一个逻辑 Tab；重复点击侧栏项
应激活已有 Tab，而不是创建副本。

建议 Tab 结构：

```text
[图标] 每周工作总结    已启用 · 下次周一 09:00
                                          [保存] [立即运行] [暂停] [...]

任务内容
  每周一读取上周发布记录和工作空间资料，生成本周运营总结……

执行时间
  每周一 09:00 · Asia/Shanghai

绑定资源
  @ 当前工作空间  @ docs/发布记录.md  @ 运营数据源

输出
  docs/周报/{yyyy}-W{week}.md

权限与确认
  可读取工作空间 · 可写入 docs/周报 · 外部提交逐次确认

最近运行
  2026-07-29 09:00  已完成
  ├─ 读取 8 个文档
  ├─ 生成 docs/周报/2026-W31.md
  └─ 耗时 2m 14s
```

Tab 包含以下区域：

1. 标题与状态。
2. 任务内容。
3. 执行时间。
4. 绑定资源。
5. 输出约定。
6. 权限与人工确认点。
7. 当前运行与历史运行。

任务编辑采用显式保存：

- 新建时显示未保存状态。
- 修改已启用任务后，Tab 显示 dirty 状态。
- 每次保存产生单调递增的 revision；运行开始时固定 revision 和定义快照。
- “立即运行”只运行最近已保存 revision；存在未保存修改时禁用并要求先保存。
- 修改时间、权限或输出位置不会静默影响正在运行的实例。
- “保存”只保存定义；首次启用必须使用“保存并在此设备启用”。
- 保存新 revision 后，当前运行继续使用旧 revision，后续运行才使用新 revision。

关闭 Tab 只关闭视图，不暂停、不删除定时任务，也不中止当前运行。

## 创建与编辑流程

### 新建

1. 用户在定时任务侧栏点击 `+`。
2. 打开新的定时任务 Tab。
3. 默认绑定当前工作空间。
4. 用户输入自然语言任务内容。
5. 用户选择时间规则、资源和输出位置。
6. 系统展示保存确认摘要。
7. 用户选择“仅保存”或“保存并在此设备启用”。

保存确认摘要必须说明：

- 所属工作空间。
- 任务什么时候运行。
- 需要读取和写入什么。
- 是否使用浏览器、数据源、Terminal 或设备。
- 哪些动作会等待人工确认。
- Studio 退出时不会运行。
- 错过后的处理策略。

### 自然语言辅助

用户可以输入：

> 每周一上午九点读取上周发布记录，生成本周运营总结，保存到 docs/周报。

系统可以解析为结构化草稿，但不能未经用户查看直接启用。结构化字段才是生效事实，
自然语言解析结果必须在 Tab 中可编辑。

### 复制到其他工作空间

定时任务不能通过修改内部 `workspacePath` 静默迁移。

“复制到工作空间”必须：

1. 选择目标工作空间。
2. 生成新的任务 ID。
3. 重新检查资源路径和输出位置。
4. 默认保持未启用。
5. 不复制本机权限授权、登录态或运行历史。

## 时间规则

第一版提供有限、可解释的计划类型：

| 类型   | 用户设置               |
| ------ | ---------------------- |
| 单次   | 日期、时间、时区       |
| 每天   | 时间、时区             |
| 工作日 | 周一至周五、时间、时区 |
| 每周   | 星期、时间、时区       |

暂不在普通界面暴露 Cron 表达式。每个任务必须显示人类可读摘要和精确的下一次运行时间。

时区属于任务定义，不能只依赖设备当前时区。设备时区变化后，Tab 必须明确说明下一次
运行是否变化。

重复任务默认禁止重叠：

- 上一次仍在运行时，不启动同一任务的新实例。
- 默认只保留一次待执行，不无限堆积。
- 用户可以在运行记录中看到“因上一实例未结束而跳过”。

## 状态模型

### 定时任务状态

```text
draft
  └─ saved
      ├─ enabled
      ├─ paused
      ├─ unavailable
      └─ deleted
```

| 状态   | 用户含义                         |
| ------ | -------------------------------- |
| 草稿   | 尚未保存，只存在于当前 Tab       |
| 未启用 | 定义已保存，但本机不会自动执行   |
| 已启用 | 本机将在下次计划时间尝试执行     |
| 已暂停 | 保留定义和历史，不再产生计划运行 |
| 不可用 | 工作空间、Agent 或必要能力不可用 |

### 单次运行状态

```text
queued → running
           ├─ completed
           ├─ failed
           ├─ cancelled
           ├─ needs-attention
           └─ interrupted

scheduled occurrence
           ├─ missed
           └─ skipped
```

每次运行必须包含：

- 稳定运行 ID。
- 定时任务 ID。
- 所属工作空间。
- 计划执行时间。
- 实际开始和结束时间。
- 当前步骤。
- 终态。
- 失败分类和脱敏错误。
- 产物引用。
- 是否由计划时间、补执行或“立即运行”触发。

“等待确认”是 `needs-attention` 的一种原因，不允许让 Agent 进程无限挂起。系统应保存
可恢复的待处理描述，结束本次主动执行；用户确认后创建有关联的新运行继续处理。

待处理动作至少固定：

- 定时任务 ID、定义 revision 和来源运行 ID。
- 所属工作空间和资源引用。
- 动作类型、目标和脱敏摘要。
- Browser Profile 等本机资源引用。
- 创建时间和过期时间。

用户确认时必须重新校验资源、页面和权限。旧页面或目标已经失效时进入“需要重新
准备”，不能使用旧确认直接提交。

## 工作空间绑定

定时任务创建时固定 `workspaceRef`：

- 侧栏只投影当前工作空间任务。
- Tab 随所属工作空间恢复和隐藏。
- 切换工作空间不迁移任务归属。
- 切换工作空间不终止后台运行。
- 工作空间目录缺失、移动或不可写时，任务进入“不可用”或“需要处理”。
- 系统不能自动猜测另一个同名目录并改绑。

如果用户关闭当前工作空间但 Studio 仍在运行：

- 已开始的任务继续收束为明确终态。
- 尚未开始的已启用任务仍属于原工作空间；到点时先验证工作空间路径和能力。
- 路径不可用时记录失败或需要处理，不切换到当前工作空间执行。

全局/未归档区域第一版不允许创建定时任务。用户必须先选择一个本地工作空间，避免
任务没有稳定资源边界和输出归属。

## 定义、启用与本机状态

“绑定工作空间”不等于“在任何设备自动执行”。

产品上必须区分：

| 数据                   | 归属                              |
| ---------------------- | --------------------------------- |
| 任务定义               | 工作空间范围                      |
| 是否在本机启用         | 当前设备                          |
| 权限授权和浏览器登录态 | 当前设备，不进入工作空间可见配置  |
| 当前运行事实           | 当前 Studio 主进程                |
| 历史运行和诊断         | 当前设备，并关联工作空间与任务 ID |

从 Git、压缩包或其他机器得到一个包含定时任务定义的工作空间时，任务默认保持“未在此
设备启用”。用户必须查看任务内容、资源和权限后显式启用，防止“打开仓库即自动执行”。

首版采用工作空间定义与本机运行事实分离的存储：

```text
workspace/
└── .cclink-studio/
    └── scheduled-tasks/
        ├── {taskId}.json
        └── ...

userData/
└── scheduled-tasks/
    ├── activations.json
    └── runs/
        ├── {workspaceId}.jsonl
        └── ...
```

工作空间任务定义默认写入仓库本地 `.git/info/exclude`，不修改用户 `.gitignore`，也
不因 Git clone 自动传播和启用。用户显式导出或复制工作空间时可以携带任务定义，但
目标设备仍必须重新检查并启用。

存储必须满足：

- 定时任务服务是定义、启用状态和运行记录的唯一领域 owner。
- 工作空间状态快照只保存 Tab 和侧栏投影，不能反向覆盖主进程运行事实。
- 任务定义不得包含密码、Token、Cookie、验证码、恢复码或第三方凭证值。
- 本机启用状态、权限和运行锁不得通过工作空间文件静默传播到其他机器。
- 持久化写入必须原子、可备份、可迁移、可恢复。

## 运行、并发与工作空间切换

第一版采用保守并发：

- 同一定时任务最多一个运行实例。
- 同一工作空间最多一个自动定时任务运行。
- 用户正在执行交互式 Agent 任务时，定时任务进入有界排队，不抢占或中止用户任务。
- 队列有最大等待时间，超时后记录为跳过或失败，不能无限等待。
- 不因为 UI 切换活跃 Tab 或工作空间而改变任务资源归属。

后台任务不能自动把用户当前工作空间、Browser Tab 或编辑器焦点切走。需要用户处理时，
使用徽标和通知；只有用户点击“查看”后才执行受控工作空间切换。

## 权限与人工确认

定时任务不能直接继承全局 `auto` 模式作为无人值守授权。任务保存时必须展示能力摘要，
运行时使用任务级策略。

首个产品闭环只允许：

- 读取绑定工作空间内明确范围。
- 写入用户声明的输出目录。
- 执行不产生外部提交的内容整理和生成。

首个产品闭环默认拒绝：

- 任意 Terminal 命令。
- Git Push 或远端写入。
- 删除、覆盖未声明文件。
- Android 设备操作。
- 浏览器读取、填写、发布、评论、私信、删除、支付和提交。
- 数据源查询及其他尚未进入首版 allowlist 的能力。
- 无法分类的工具或路径。

后续阶段可以逐项开放只读数据源和浏览器准备，但每项都必须增加独立能力声明、失败
降级和真人验收，不能通过扩大“读取工作空间”权限顺带放行。

高风险动作必须经过产品级确认，权限模式不能绕过。确认卡至少展示：

- 定时任务。
- 所属工作空间。
- 本次运行。
- 目标平台或资源。
- 将执行的动作。
- 使用的文件和账号备注。

确认超时不能伪装成“仍在等待”。系统应转为明确的“需要处理”，并保留恢复入口。

## App 内统一调度、退出和错过执行

首版产品文案必须明确：

> 定时任务只在 CCLink Studio 运行期间执行。

这里的“运行期间”表示 Electron 主进程仍存活且 App runtime 已完成启动。窗口最小化
时 App 仍可调度；按当前退出语义关闭最后一个主窗口会退出 App，调度也随之停止。

统一调度规则：

- 只有 `ScheduledTaskService` 计算下一次到期时间和创建运行。
- 调度器通过 App runtime 注册，启动、失败回滚、停止和窗口重建使用同一生命周期声明。
- App 开始退出后立即停止认领新运行并清除内存 timer。
- 已开始运行必须终止或有界收束，持久化为完成、失败、取消或中断之一。
- App 退出后不保留调度器、Agent 子进程、后台 Helper 或系统计划任务。
- App 下次启动时从持久化事实对账，不假装恢复已经消失的进程。

默认规则：

- 单次任务错过后标记为“已错过”，由用户选择立即运行或跳过。
- 重复任务只考虑最近一次错过，不重放所有历史周期。
- 默认宽限时间为 30 分钟；在宽限时间内启动 Studio 时可以补执行一次。
- 超过宽限时间后不自动补执行，避免启动时集中执行大量旧任务。
- 运行中正常退出时优先有界收束；无法完成或崩溃后，旧运行标记为“已中断”，不能恢复
  成假运行态。
- 设备休眠恢复后重新计算到期任务，并应用相同宽限规则。
- Studio 已退出时不请求系统唤醒，也不产生新的运行记录；下次启动时才判断是否错过。

托盘常驻、开机启动和操作系统后台服务不在当前路线承诺中。如果未来重新提出，必须
作为独立产品阶段和 ADR 评审退出语义、资源占用、更新、权限、卸载残留和多平台差异，
不能复用首版名义静默加入。

## 通知与回到任务

通知只报告可操作结果：

- 任务已完成，并列出主要产物。
- 任务失败，并给出脱敏原因。
- 任务需要登录、确认或修复资源。
- 任务已错过。

点击通知：

1. 定位任务所属工作空间。
2. 如果需要切换工作空间，执行受控 transition。
3. 激活已有定时任务 Tab，或打开该任务的新视图。
4. 定位到对应运行记录。

通知不能自动打开网页、提交动作或抢占用户当前输入焦点。

## 命令与上下文操作

定时任务的各入口复用统一 command：

| Command ID 建议                 | 用户操作             |
| ------------------------------- | -------------------- |
| `scheduledTask.create`          | 新建定时任务         |
| `scheduledTask.open`            | 打开定时任务 Tab     |
| `scheduledTask.save`            | 保存任务定义         |
| `scheduledTask.enableLocal`     | 在此设备启用         |
| `scheduledTask.pauseLocal`      | 在此设备暂停         |
| `scheduledTask.runNow`          | 立即运行已保存版本   |
| `scheduledTask.cancelRun`       | 终止当前运行         |
| `scheduledTask.copyToWorkspace` | 复制到另一个工作空间 |
| `scheduledTask.delete`          | 删除任务             |
| `scheduledTask.copyDiagnostics` | 复制脱敏诊断         |

工具栏、快捷键、命令面板和上下文菜单必须引用同一 command 定义和执行入口。新增 target、
command、contribution 和 owner 必须登记到 Context Action inventory。

## 产品里程碑

以下里程碑只按用户可见闭环命名，不以 Schema、测试或重构代替产品进度。

### M8.1：创建和管理工作空间定时任务

用户可以：

- 从 Activity Bar 打开定时任务侧栏。
- 在当前工作空间新建任务。
- 在独立 Tab 编辑、保存、启用和暂停。
- 关闭并重新打开 Tab 后继续看到同一个任务。

真人验收：

1. 打开工作空间。
2. 新建一个每天 09:00 的任务。
3. 保存并启用。
4. 关闭 Tab。
5. 从侧栏重新打开并确认内容、状态和下次运行时间一致。

### M8.2：定时生成工作空间产物

用户可以：

- 点击“立即运行”验证任务。
- 在 Studio 运行期间按计划自动执行。
- 在任务 Tab 查看当前步骤、结果和历史。
- 打开生成的 Markdown 产物。

真人验收：

1. 创建一个几分钟后运行的 Markdown 周报任务。
2. 切换到其他 Tab 等待。
3. 到点后任务自动运行。
4. Activity Bar 显示状态。
5. 回到任务 Tab 查看成功记录并打开真实生成文件。
6. 再创建一个几分钟后运行的任务，在到点前退出 Studio。
7. 确认任务没有在 App 退出后执行，重启后显示明确的错过状态。

### M8.3：工作空间切换与失败恢复

用户可以：

- 在任务运行期间切换工作空间，任务不串工作空间、不抢焦点。
- 查看错过、中断、目录缺失和 Agent 不可用等明确状态。
- 对可恢复失败执行重试或立即运行。

真人验收：

1. 在工作空间 A 启动任务。
2. 切换到工作空间 B。
3. 确认 B 的侧栏没有 A 的任务。
4. 切回 A，确认任务仍有明确终态和正确产物。
5. 模拟一次工作空间不可用并确认显示可操作失败。

### 后续产品阶段：浏览器准备与人工确认

用户可以：

- 定时打开指定 Profile 并准备页面内容。
- 在不可逆提交前收到“需要处理”通知。
- 回到任务 Tab 查看待确认动作。
- 明确确认后继续，或拒绝并留下运行记录。

真人验收：

1. 创建一个几分钟后准备平台草稿的任务。
2. 到点后自动打开正确 Profile 并填写草稿。
3. 最终发布动作不自动执行。
4. 用户从通知回到任务 Tab。
5. 用户确认后完成提交，或拒绝后看到已取消记录。

## 工程准备度

工程准备度与产品里程碑分开报告。预期准备项包括：

- 共享 contract、Zod schema 和持久化版本。
- `ScheduledTaskService` 单一状态 owner。
- 主进程生命周期注册和对称清理。
- App 内单一 timer 所有权；禁止系统调度注册和退出后残留进程。
- Agent 运行事件订阅与稳定 correlation。
- 任务级工具 allowlist 和路径校验。
- renderer IPC 投影、Tab 恢复和状态对账。
- Context Action contribution 与 inventory 门禁。
- 假时钟、时区、休眠、错过、崩溃恢复和并发测试。
- 退出 smoke：App 退出后无 Agent 子进程、后台 Helper、登录项或系统计划任务遗留。
- `pnpm verify` 与受影响 smoke。

这些准备项完成只表示实现具备交付准备度；对应真人验收未通过时，不得把 M8.x 标记为
完成。

## `/grilling`

结论先说：侧栏和 Tab 只是入口，真正决定产品是否可信的是工作空间归属、设备级启用、
运行状态和确认恢复是否一致。

实现前必须回答：

1. 一个从 Git 克隆得到的任务定义，是否可能未经确认就在本机执行？答案必须是否。
2. 关闭 Tab、切换工作空间、关闭主窗口分别意味着什么？三者不能共用一个含糊的
   “关闭任务”语义。
3. 用户修改已启用任务但没有保存时，到点执行哪个版本？只能执行最近已保存版本。
4. 同一任务上次还没结束时，是排队、跳过还是并发？第一版必须禁止并发并留下记录。
5. 用户三天没打开 Studio 后，是补一次、全部补跑还是跳过？默认只能有界补最近一次。
6. 任务需要确认但用户数小时不在电脑前，是否仍占用 Agent 进程？不能；必须收束为
   可持久化的“需要处理”。
7. 任务绑定的文件被移动、数据源被删除或浏览器登录失效时，是否会猜测替代资源？
   不能；必须失败并让用户重新绑定。
8. 定时任务写文件时，如何防止越过工作空间和声明输出目录？必须由工具宿主硬校验，
   不能只靠 prompt。
9. Activity Bar 的全局徽标和当前工作空间侧栏如何避免状态不一致？运行事实必须由
   主进程 owner 提供，renderer 只做投影。
10. M8.1 的页面做好但任务尚不能真实到点执行时，能否汇报“定时任务已完成”？不能；
    只能说明用户已经可以创建和管理资源。
11. 为了“更准时”是否值得注册系统服务或后台 Helper？首版答案是否。App 不存活就不
    执行，下次启动只做有界错过对账。
12. App 退出后是否还能找到定时任务相关子进程、登录项或系统调度记录？答案必须是否；
    否则违背低负担、无遗留的产品选择。

下一步最该做的是按已确认边界拆出首个纵向闭环：在任务 Tab 保存一个几分钟后执行的
Markdown 生成任务，由 App 主进程到点触发，并在退出后不执行、不留系统遗留。侧栏、
Tab、真实产物和运行历史一起验收，不能先做系统调度或横向基础设施。
