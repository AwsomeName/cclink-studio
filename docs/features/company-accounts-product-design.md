# AI 账目助理核心产品设计

更新日期：2026-10-09。状态：重新设计提案，未实现，未排期。复用前期专业软件调研结论；以本文件为最新产品方案，既有六页示意暂存，尚未按本方案更新。

## 用户能够验收的结果

用户提供一个真实月份的账单、凭证和研发支出资料，使用 AI 准备账目并处理疑点，人工确认后能查看年、月、周、日收支与项目支出；通过对话或表单提交一笔垫付报销，审批与真实付款分别记录，归还后不重复增加项目费用；能查看缺项、待收待付并处理提醒，导出给现有代账，再从备份恢复资料及历史。

当前缺口：以上为设计目标，Studio 尚未形成真实账目闭环。账单来源、现有代账交付、身份和协作、存储以及成本口径仍需确定。第一版先采用本地单人管理候选边界，批准人名称不能代替真实权限身份。

## 产品定位与工作空间

AI 账目助理帮助不熟悉财务的经营负责人记录业务、管理研发支出、核对资金、办理内部申请并理解结果。以内部经营账为主，保留现有代账交接；正式财税复核、会计核算和申报单独记录，不将内部确认冒充正式入账。

复用 Studio 普通工作空间，通过说明文档和初始化配置记录公司、账户名称、分类、研发项目、工作规则和提醒偏好。暂不要求用户建立额外财务目录树，不引入新的 Workspace 类型或独立 App。数据和原始凭证必须可完整迁移、导出和备份，不进入 Studio 源码仓库或默认上传云端。

说明文档配置工作规则，结构化账目保存事实，聊天只作为输入和解释入口；三者不能互相代替。存储技术尚未选择，独立数据库文件与纯文件方案仍需比较。

## 六个核心功能入口

| 入口 | 用户的问题与动作 | 页面内容与闭环 |
| --- | --- | --- |
| 经营报表 | 今天、本周、本月、本年收了多少、付了多少？ | 年/月/周/日/自定义期间；收支、净流入、类别趋势与项目比较；按账户、项目和状态筛选；从汇总到明细、原件，导出口径一致 |
| 研发项目 | 每个眼镜型号或批次花在哪里，还有多少预算？ | 项目列表与详情；器件、采购、打样、服务、报销关联；预算、已确认项目费用、实际付款、待付款分开；跨项目分摊保留明细 |
| 收支账 | 每笔钱的来龙去脉是否清楚？ | 收款/付款/退款/互转登记；原始流水导入、去重、业务匹配、核对、人工确认及更正；区分公司账户与个人垫付 |
| 申请与审批 | 报销或付款申请怎样提交、批准和跟进？ | 对话或表单准备报销/付款申请；草稿、待审批、退回、批准待付款、部分付款、已付款及作废；附件、理由与操作历史；真实付款再关联到收支账 |
| 待收待付 | 客户还欠多少、供应商或员工还没付多少？ | 来源单据、对象、总额、已结算、余额、到期日；收款或付款关联并结清；不从 AI 猜测或单张未付发票直接认定债务 |
| 资料与交接 | 证据在哪里，怎么交给代账？ | 凭证关联、缺项清单、月度资料包、经营报表导出、实际交接与财务返回结果；备份、恢复与修改历史作为辅助入口 |

经营报表是默认主视图；AI 对话常驻现有 Agent 面板，具体申请以对话框或侧面表单展开，待办通过通知与可展开清单呈现。用户不必在多个页面重复登记同一业务。

## AI 与主动提醒贯穿各入口

### AI 可以准备和解释的工作

- 导入授权范围内的账单与凭证，提取字段、建议分类和项目、识别疑似重复并匹配已有业务。
- 将“我替眼镜 A 买了器件 800 元”等描述转成可核对的申请草稿；缺日期、金额、用途或附件时提问，不猜测补齐关键字段。
- 回答基于已确认数据的收支和项目问题，提供统计期间、口径、资料覆盖及关联明细；计算使用结构化记录，不能让模型编造合计。
- 准备交接资料与疑点说明；敏感凭证进入云端模型前，需要明确模型数据处理范围和授权。

用户拥有账目确认、申请提交、审批与关键更正权；批准不等于实际付款，经营确认不等于财税复核。AI 不能直接确认账目、批准自己的申请、转账或提交申报。确认和申请绑定具体版本，关键更正留痕并重新确认。

### 提醒必须指向可处理事项

待确认、缺凭证、金额不一致、疑似重复、申请待审批、批准后未结算、已登记到期的欠款、用户设定的预算阈值、月度核对和备份失败均可成为提醒。每项显示对象、事实依据、日期及下一步，可查看、处理、暂缓或关闭。

同一事实未变化时不反复提醒；暂缓不修改业务状态。日期来自用户规则或已确认单据，不由模型推测法定期限。复用 Studio 既有定时及运行能力，不创建另一套任务状态所有者。本地关闭或休眠期间不保证送达，恢复后检查错过事项并显示最后数据更新时间。

## 数据关联和报表口径

用户看到六个入口，但它们引用相同的业务记录、收付记录、项目、原件与确认历史。文件导入、AI 草稿和汇总不能形成并行账本。

1. 实际收支按真实公司收付日期统计，未确认流水另列。借款、出资、退款和内部账户互转有各自类型，不能一律当经营收入；多个公司账户间转账在合并报表中抵消。
2. 项目已确认费用与公司实际付款分别展示。采购预付款、未消耗库存、退款与跨项目分摊需要明确业务处理规则，尚未纳入时显示局限，不宣称完整项目成本或利润。
3. 待收待付由已确认业务责任及结算记录计算，提交申请本身不形成已确认债务。批准报销若同时完成了有权限的内部业务确认，可登记应付员工；财税复核仍独立。
4. 一个业务可有多次收付，一个收付可分配到多个业务；报销单、银行流水、发票与采购单关联到同一业务，不能各生成一次费用。
5. 项目预算初期可用已确认费用比较；未结算不等于未占预算。预算是否计入采购承诺、库存和预付款另行设计，所有金额须标明口径。
6. 资料未导入显示“资料不完整”，不能当零；已确认、待确认和正式财税已复核可独立查询。所有筛选与导出保持一致。

## 从一笔器件报销理解闭环

用户对话说明为眼镜 A 垫付 800 元并附资料 → AI 准备申请草稿 → 用户核对后提交 → 有权限的负责人审阅并批准、完成内部业务确认 → 项目已确认费用 800 元、应付员工 800 元、公司现金支出 0 元 → 公司真实归还并核对付款凭证 → 应付结清、公司现金支出 800 元、项目费用仍为 800 元 → 这笔业务进入相应期间报表并连同凭证导出。

退回申请保留原因并重新提交；只归还 300 元则仍欠 500 元；收到重复截图先隔离；金额或项目更正保留原版本并重新确认。单人管理时也可按该过程自查，但不伪称已完成多人审批。

## 最小首版与后续能力

首版候选：本地单人管理，账单与凭证导入、AI 整理、人工确认、多周期经营报表、研发项目费用与简单预算、基本报销和付款申请、人工审批记录与实际支付匹配、由已确认业务产生的简单待收待付、提醒、导出交接和可恢复备份。首版必须形成一个月份及一笔报销的完整闭环，不能先交付六个静态页面。

后续候选：多人协作与真实角色权限、多级审批、完整采购收货和器件库存、固定资产、工资、正式会计核算及税务系统衔接、银行直连。它们有独立验收目标，不能默认为首版已具备。

开发顺序按一条业务贯通导入、确认、报表、导出，再贯通垫付申请、审批、结算和提醒；并非按六个入口分别做完空页面。首版待收待付只接入明确业务来源，不开展完整 ERP 或通用财务框架。

## 工程边界与验收

账目服务是业务、关联、确认和版本事实的唯一写入所有者。复用现有 Workspace、Tab、Agent、定时运行与 IPC 机制，遵守共享 schema、主进程受控文件操作、串行原子持久化及可迁移恢复；UI 和 Agent 不直接写文件绕过确认。监听、运行与工作空间生命周期对称，切换时解绑旧作用域。

权限收窄到用户选择的数据；审批依赖可信操作者身份。诊断覆盖导入、匹配、确认、写入、提醒和恢复，但不泄露账户、交易明细或原件。账目能力失败可诊断和重试，不阻断 Studio 其他本地能力。写入失败不能标记成功；损坏资料隔离、汇总标明缺失范围。

产品验收用真实月份核对收支和项目明细，验证重复导入、退款、账户互转、部分付款、申请退回、更正重确认、提醒去重与休眠后补查；交接资料可被使用，备份能恢复原件与历史。工程门禁通过与上述产品验收分别记录。持续超过 60 分钟没有新增可验收能力时停止扩张并做偏航检查。

## 继续讨论的三个关键决策

1. 使用者是谁：暂按单人管理已有资料，不能据此实现员工在线报销和多人审批。
2. 输入是什么：需了解实际银行/微信/支付宝账单格式、凭证保存与现有代账月度交付。
3. 数据怎样携带和恢复：存储形式、目录要求、权限与备份位置未定；先确保用户能导出和完整恢复，再决定技术。

本轮验证仅为需求与方案一致性审查，未运行功能测试或做真实财务验收；节省年度费用的效果尚待真实流程比较。
