## 一、定义

**Owner 是对一件事务负责到底的负责人。** 你把一件事交给它，它明确目标和完成条件，安排工作，派执行会话去做，用证据核对结果，最后交付成品；做不下去时说清楚卡在哪、在等谁、需要谁做什么。

- **一件事务对应一个 Owner。** Owner 不创建、不委派、不管理其他 Owner。
- **执行会话只是它手下的人手。** 一件事务可以有多个执行会话（A、B、C…），由 Owner 按子任务之间的依赖决定续用还是新开；一个会话结束，Owner 对这件事的责任仍在。

## 二、Owner 与 Agent 的根本区别

|              | Agent（会话）          | Owner                          |
| ------------ | ---------------------- | ------------------------------ |
| 负责对象     | 一段会话、一次运行     | 一件事的最终结果               |
| 推进方式     | 你说一步，它做一步     | 自己定计划，自己推进           |
| 完成标准     | 运行结束，自述“做完了” | 证据满足完成条件，成品已落盘   |
| 生命周期     | 随会话结束             | 跟着事务走，跨会话、跨重启     |
| 你和它的关系 | 你是操作者             | 你是交办人，只在需要决策时出面 |

**Agent 是干活的，Owner 是负责的。**

## 三、产品思路

1. **以事务为中心，不以聊天为中心。** 页面先回答：做到哪了，卡在哪，在等谁，交付了什么。
2. **事先约定，事后按证据交付。** 动手前约定范围、交付物、验收标准和时间限制；交付时逐条核对证据，不认执行会话的自述。
3. **按依赖分配会话。** 连续、依赖前一步结果的子任务续用同一个会话；不相干、能独立完成的子任务开新会话，不把无关上下文堆进一个会话。
4. **只在必要时找你。** 查资料、补查、续用或新开会话、核对由 Owner 自行决定；只有改约定、需要你提供资料或授权、涉及外部副作用、出故障时才停下来问你。
5. **过程留痕，可以恢复。** 派工、回执、判断和证据全部落盘；离开、重启、换会话后仍是同一件事、同一个负责人、同一份进度，且不重复派工。
6. **权限按事务收窄。** 偏好设置不带任何权限；读取本地资料必须由你明确授权给这一件事务，可随时撤销。

## 四、核心功能

1. **交办与约定。** 你说目标，Studio 立即建好事务目录。Owner 给出约定卡：范围、交付物、验收依据、时间限制。可讨论修改，确认一次后生效；约定改版须重新确认。
2. **派工与执行。** 每次派工先定会话：
   - **续用**：本步依赖某个会话已读到的内容或结论（例如读完流水线文档，再沿选中的一级追 RTL），交给那个会话。
   - **新开**：本步与已有会话的工作互不依赖（例如分别调研 Ibex 与 CVA6、项目定位与许可证核对），开一个新会话。原会话无法继续时也新开，并写明交接内容。
   - 每个执行会话有一句「负责什么」，做完自己那块就收尾，不接无关的活；之后有与它相关的新问题可以再续用。
   - 派工单写明：交给哪个会话及原因、本步问题、可用资料与权限、要交回什么、怎样算完成。会话选择作为一条判断记入事务，看板与 `调度.md` 可见。
   - 新开会话在启动前自动选用可用的 Agent（优先 Codex，不可用时 Claude）；已开始的运行不中途换 Agent。
3. **核对与补查。** 每份回执对应到委托、会话和运行，按该派工单写明的交回要求和完成标准逐项验收。不够就写明缺哪条，按依赖决定续用原会话补查还是另开会话。
4. **等你决定。** 待决卡写明为什么问你、各选项的影响。只有明确选择才算决定；阅读、提问、返回列表都不消耗待决卡。
5. **交付。** 成品写入磁盘、引用全部核对通过后才标为「已交付」；每条引用可定位到证据原文的具体行。
6. **持续可问。** 右侧始终是本事务的 Owner 主对话；执行中随时可问“为什么、到哪了”，提问不打断工作。
7. **事务目录。** `事务.md`、`事务配置.md`、`调度.md`、`工作记录.md`，加 `资料/`、`交付物/`。离开 Studio 也能读懂；手改文件不会触发派工或被当成确认。
8. **Owner 设置。** 新事务的默认保存位置、常用参考目录与来源。只决定默认值，不带任何权限。

## 五、界面

1. **入口**：顶栏右上「Owner」，不打开项目也能进。顶栏数字只统计确实需要你处理的事务。
2. **列表**：先列「等我确认 / 等我提供资料」，再列「进行中」「已交付」。每行写清等你什么、Owner 在做什么或交付了什么。可在此新建事务、进入 Owner 设置。
3. **事务内三栏**：左侧固定侧栏（事务进度、可读目录、已落地文档、保存位置）；中间事务看板与文档标签，看板列出各执行会话负责什么、运行到哪；右侧本事务的 Owner 主对话（始终是 Owner，不换成执行会话）。

## 六、0.1 边界

- 首个场景：开源芯片调研，只读公开资料，不编译、不仿真。
- 一件事务可有多个执行会话，但同一时间只运行一个：独立子任务排队依次执行，并行留到后续版本。只展示一张待决卡。
- 不做：多个 Owner 协作、AI 员工档案、商业模板、跨设备恢复执行。

## 七、开发版实现进度（2026-11-21）

- **已有：** 交办 → 确认约定 → 执行会话 A 取证与补查 → 交付 → 引用定位原文；保存失败续写原稿；重启后恢复且不重复派工。界面按 [v2 效果图](../design/owner-0.1/v2/README.md) 落地了入口与列表（01、02）、约定卡（03）、三种状态与当前步骤（04）、交付卡（06）、文档标签（07）、两步确认的只读目录授权（08）和 Owner 设置（09：新事务保存位置、常用参考目录登记、常用来源、顶栏计数），以及看板标题行与问题卡片里的「复制 Owner 诊断」（10–12，只含本事务事实与相关框架日志，不含聊天、证据和交付正文，经统一脱敏）。偏好与目录登记保存在 `userData/owner-directories/preferences.json`，由主进程 `OwnerPreferences` 唯一写入；目录只能经系统选择器登记，偏好不授予读取权限。
- **未有：** 按依赖分配多个执行会话（现为固定单一会话 A，且未接入启动前自动选择 Agent）；派工单的交回要求与完成标准；待决卡（05）及其约定改版流程；执行会话读取本地参考目录；截止时间与投入上限；常用来源偏好尚未改变取证范围（取证仍只读公开 GitHub 仓库）。验收步骤见 `docs/testing/owner-workbench-sidebar.md`。
- 自研，不引入 AgentOp 或 pi-missions 代码。参见[事务流程与六步效果图](../design/owner-0.1/README.md)、[固定侧栏与存储设计](../design/owner-0.1/workbench-mode.md)。

验收动作：交办一次开源芯片调研，确认范围、交付物和只查官方资料。连续的初查、续查与补证续用同一执行会话；独立子任务另开会话，看板写明每个会话负责什么、为什么新开；运行结束但依据不足时，事务仍在进行。分别打开主对话、来源和最终简报核对。另测原会话确实无法续用时的跨会话交接。不用开会话的数量衡量进展。

## 与角色的关系

> **领域上分离，产品上组合，交付上保持一个 Studio。**
>
> 角色是可复用人格模板；员工在一件事务内持续负责，按需使用已授权的资源与能力。

角色与员工不合并为同一实体。普通临时会话可以直接使用角色，不必创建员工；一个角色可以
被多个 Owner 复用。0.1 从交办事务开始，角色引用、Skills 和资源授权按需关联；不要求用户先创建员工档案，各领域仍保持不同状态所有者。

首版不建设员工中心、员工配置或商业模板。

## 概念边界

| 概念                    | 回答的问题                         | 拥有的事实                                                   | 明确不拥有                                              |
| ----------------------- | ---------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------- |
| 角色                    | “以什么人格、视角和原则处理？”     | Manifest、`SOUL.md`、行为边界、建议 Skill 引用和版本         | 真实账号、资源授权、工具权限、任务与执行记录            |
| Owner                   | “谁负责这件事务，用哪些会话推进？” | 单一事务的关联、执行会话的关联、角色与授权引用、能力收窄策略 | 其他 Owner、角色正文、资源本体、事务领域状态和 Run 状态 |
| Skill                   | “采用什么可复用流程？”             | Skill 定义与版本                                             | 人格、资源凭证与工具权限                                |
| 资源                    | “具体可以访问什么？”               | 网站、账号、文件、数据源或其他资源事实                       | 员工职责和角色人格                                      |
| 能力                    | “系统当前能执行什么类型的动作？”   | 能力实现、可用状态与诊断                                     | 对具体员工的资源授权                                    |
| 事务/定时任务           | “要持续完成什么、何时触发？”       | 流程、触发、终态、证据和恢复事实                             | 员工人格、资源定义和工具实现                            |
| Agent Run / BrowserTask | “这一次实际执行了什么？”           | 单次执行状态、回执、错误与诊断                               | 员工长期配置                                            |

“员工集成资源和能力”统一解释为：员工保存稳定引用和经过用户确认的授权，并对现有能力做
范围收窄；它不能把资源、凭证、Skill、事务流程或工具模块复制成自己的内部定义。

## 组合关系

```text
角色「公共治理者」
  ├─ 可直接应用到普通会话
  ├─ 可被员工「政策监测员」引用
  └─ 可被员工「社区反馈分析员」引用

员工「政策监测员」
  ├─ roleRef           -> 固定的角色版本
  ├─ skillRefs          -> Skill Registry 中的稳定引用
  ├─ resourceGrants     -> 资源服务中的显式授权引用
  ├─ capabilityPolicy   -> 对系统能力的收窄范围
  ├─ 负责的事务          -> 一件，例如「跟进本次政策征求意见」
  └─ 执行会话            -> 按需使用；各自交回结果，不再派生 Owner
```

如果未来把会话绑定到员工，会话执行者必须采用互斥关系：普通会话绑定角色，员工会话绑定
员工，不能同时保存一份可独立修改的 `roleRef` 和 `employeeRef`。员工绑定时由员工配置解析
角色版本；要临时脱离员工人格，应先显式解除员工绑定，避免出现两个角色事实源。

## 权限与状态所有权

员工只能缩小范围，不能扩大现有授权：

```text
本次有效能力
= 系统当前可用能力
∩ 用户启用的能力
∩ 员工允许的能力范围
∩ 本次任务 Scope
∩ 产品级人工确认边界
```

状态所有权保持如下：

- `AgentRoleRegistry` 唯一拥有角色 Manifest、`SOUL.md` 解析结果和版本；员工只持 `roleRef`。
- Skill Registry 唯一拥有 Skill 定义和安装状态；员工只持 `skillRefs`。
- `WebResourceService`、文件、数据源等资源领域继续拥有资源与凭证；员工只持可撤销授权引用。
- `WebAffairService` 唯一拥有网页事务流程、节点、证据和终态；员工只持分配引用和只读投影。
- Agent、BrowserTask 与定时任务领域分别拥有运行和触发事实；员工只持关联 ID 和可重建投影。
- 现有权限系统和主进程确认边界仍是硬上限；角色、`SOUL.md`、Skill 或员工配置均不能绕过。

## 产品入口原则

Owner 0.1 的事务入口与角色配置入口分开：

- 角色中心负责发现、理解和应用人格模板；继续使用全局唯一的角色配置 Tab。
- 用户从事务直接看目标、所用资源、各会话已交回的结果、当前阻塞及下一步，无需先找员工配置或翻阅对话。
- “新建事务”可通过主对话交办，中央回显本次目标、完成条件、资源范围与待确认项；浏览或选择角色不会增加授权。
- 普通 Composer 继续允许直接使用角色；员工工作应通过明确的员工上下文进入和退出。

## 当前商业与交付范围

Studio 始终只有一个 GPL-3.0-only 桌面 App。当前所谓“商业版本”仅保留 CCLink 托管远程
功能域：按需登录的账号、设备与消息网络、远程请求、RemoteProvider、远程工作空间和后续
逐步验收的远程 Agent/PTY 闭环。远程服务的授权和收费由服务端强制。

当前不做：

- 通用员工系统、独立 Agent 运行时和新的员工 IPC；
- 托管员工、员工市场、商业员工模板、运营平台适配器和团队协作；
- 第二套商业桌面 App 或商业层对 Main、Preload、Renderer 的整文件覆盖；
- 用客户端 entitlement 门控角色、Skill、事务、定时任务、浏览器等本地能力；
- 因员工概念提前改变现有角色、资源、能力、事务或定时任务状态所有权。

## 验收门禁

本轮已获开工授权。第一项产品验收是上文的「开源芯片调研」：Owner 能否在 Studio 主窗口内核对、补证并交付有依据的结果。配置、Schema、IPC 或空员工列表均不能替代这项验收。

失败必须显式降级：角色版本缺失时禁用员工并要求迁移；资源授权被撤销时停止相关工作；能力
不可用时在运行前预检；需要人工确认的定时执行必须暂停等待，不能因“员工自动运行”而绕过。

## `/grilling` 结论

- 合并角色与员工会让切换人格可能同时切换权限，是不可接受的隐式授权路径。
- 完全割裂二者会造成重复配置；正确方式是员工引用固定角色版本，产品流程组合、领域状态分离。
- 把员工留在另一套商业桌面代码中会重新制造生命周期和状态所有权分叉；未来即使重启，也只能
  在单一 Studio 中通过稳定 contract 接入。
- 首版验证本机简报交付，不扩张角色、Skill、远程权限或通用编排。
