# AI 员工领域边界与暂停决定

> 状态：产品与领域边界已确认；功能暂停，未进入实现或排期。
>
> 最后更新：2026-08-13。
>
> 关联文档：`docs/architecture.md`、`docs/features/agent-role-configuration.md`、
> `docs/features/agent-system.md`、`docs/features/scheduled-tasks.md`、
> `docs/features/ai-web-affairs-agent.md`。

## 结论

> **领域上分离，产品上组合，交付上保持一个 Studio。**
>
> 角色是可复用人格模板；员工是引用角色、资源和能力并可被持续分配工作的执行主体。

角色与员工不合并为同一实体。普通临时会话可以直接使用角色，不必创建员工；一个角色可以
被多个员工复用。未来如果提供员工产品，创建员工应从选择角色开始，在同一产品流程中继续
绑定 Skills、资源授权、能力范围和工作，但底层仍保持不同状态所有者。

当前只冻结这个领域决定，不交付员工中心、员工配置、员工运行或员工商业模板。

## 概念边界

| 概念 | 回答的问题 | 拥有的事实 | 明确不拥有 |
| --- | --- | --- | --- |
| 角色 | “以什么人格、视角和原则处理？” | Manifest、`SOUL.md`、行为边界、建议 Skill 引用和版本 | 真实账号、资源授权、工具权限、任务与执行记录 |
| 员工 | “谁持续负责哪些工作，可以使用哪些已授权资源和能力？” | 稳定身份、职责、固定角色版本引用、授权引用、能力收窄策略、工作分配引用和展示投影 | 角色正文、资源本体、工具实现、事务状态和 Run 状态 |
| Skill | “采用什么可复用流程？” | Skill 定义与版本 | 人格、资源凭证与工具权限 |
| 资源 | “具体可以访问什么？” | 网站、账号、文件、数据源或其他资源事实 | 员工职责和角色人格 |
| 能力 | “系统当前能执行什么类型的动作？” | 能力实现、可用状态与诊断 | 对具体员工的资源授权 |
| 事务/定时任务 | “要持续完成什么、何时触发？” | 流程、触发、终态、证据和恢复事实 | 员工人格、资源定义和工具实现 |
| Agent Run / BrowserTask | “这一次实际执行了什么？” | 单次执行状态、回执、错误与诊断 | 员工长期配置 |

“员工集成资源和能力”统一解释为：员工保存稳定引用和经过用户确认的授权，并对现有能力做
范围收窄；它不能把资源、凭证、Skill、事务流程或工具模块复制成自己的内部定义。

## 组合关系

```text
角色「公共治理者」
  ├─ 可直接应用到普通会话
  ├─ 可被员工「政策监测员」引用
  └─ 可被员工「社区反馈分析员」引用

员工「政策监测员」
  ├─ roleRef           -> 固定的角色版本
  ├─ skillRefs          -> Skill Registry 中的稳定引用
  ├─ resourceGrants     -> 资源服务中的显式授权引用
  ├─ capabilityPolicy   -> 对系统能力的收窄范围
  └─ assignmentRefs     -> 事务和定时任务的分配引用
```

如果未来把会话绑定到员工，会话执行者必须采用互斥关系：普通会话绑定角色，员工会话绑定
员工，不能同时保存一份可独立修改的 `roleRef` 和 `employeeRef`。员工绑定时由员工配置解析
角色版本；要临时脱离员工人格，应先显式解除员工绑定，避免出现两个角色事实源。

## 权限与状态所有权

员工只能缩小范围，不能扩大现有授权：

```text
本次有效能力
= 系统当前可用能力
∩ 用户启用的能力
∩ 员工允许的能力范围
∩ 本次任务 Scope
∩ 产品级人工确认边界
```

状态所有权保持如下：

- `AgentRoleRegistry` 唯一拥有角色 Manifest、`SOUL.md` 解析结果和版本；员工只持 `roleRef`。
- Skill Registry 唯一拥有 Skill 定义和安装状态；员工只持 `skillRefs`。
- `WebResourceService`、文件、数据源等资源领域继续拥有资源与凭证；员工只持可撤销授权引用。
- `WebAffairService` 唯一拥有网页事务流程、节点、证据和终态；员工只持分配引用和只读投影。
- Agent、BrowserTask 与定时任务领域分别拥有运行和触发事实；员工只持关联 ID 和可重建投影。
- 现有权限系统和主进程确认边界仍是硬上限；角色、`SOUL.md`、Skill 或员工配置均不能绕过。

## 产品入口原则

如果未来重启员工功能，角色中心与员工中心应当分开，但创建流程可以组合：

- 角色中心负责发现、理解和应用人格模板；继续使用全局唯一的角色配置 Tab。
- 员工中心负责持续执行主体、职责、角色引用、资源授权、能力范围、任务分配和运行投影。
- “创建员工”从选择角色开始，再配置 Skills、资源、能力和工作；不能把员工混进角色下拉框，
  也不能让浏览角色详情意外改变员工授权。
- 普通 Composer 继续允许直接使用角色；员工工作应通过明确的员工上下文进入和退出。

## 当前商业与交付范围

Studio 始终只有一个 GPL-3.0-only 桌面 App。当前所谓“商业版本”仅保留 CCLink 托管远程
功能域：按需登录的账号、设备与消息网络、远程请求、RemoteProvider、远程工作空间和后续
逐步验收的远程 Agent/PTY 闭环。远程服务的授权和收费由服务端强制。

当前不做：

- AI 员工 UI、员工 Store、员工服务、员工 IPC 或员工运行时；
- 托管员工、员工市场、商业员工模板、运营平台适配器和团队协作；
- 第二套商业桌面 App 或商业层对 Main、Preload、Renderer 的整文件覆盖；
- 用客户端 entitlement 门控角色、Skill、事务、定时任务、浏览器等本地能力；
- 因员工概念提前改变现有角色、资源、能力、事务或定时任务状态所有权。

## 重启门禁

未来只有在用户重新确认员工功能进入范围后才启动设计和实现。开始前必须先定义用户可执行的
最小纵向验收，例如：创建一个本地员工、选择固定角色版本、显式授权一项资源、选择能力子集、
分配一个任务，并能在执行回执中对账员工、角色、资源、能力和人工确认。然后才允许设计
`EmployeeRef`、状态所有者、IPC、持久化和 UI；不得用内部 Schema 或空员工列表冒充产品里程碑。

失败必须显式降级：角色版本缺失时禁用员工并要求迁移；资源授权被撤销时停止相关工作；能力
不可用时在运行前预检；需要人工确认的定时执行必须暂停等待，不能因“员工自动运行”而绕过。

## `/grilling` 结论

- 合并角色与员工会让切换人格可能同时切换权限，是不可接受的隐式授权路径。
- 完全割裂二者会造成重复配置；正确方式是员工引用固定角色版本，产品流程组合、领域状态分离。
- 把员工留在另一套商业桌面代码中会重新制造生命周期和状态所有权分叉；未来即使重启，也只能
  在单一 Studio 中通过稳定 contract 接入。
- 当前最重要的取舍是保持暂停：继续完成角色、Skill 和远程功能的既有纵向闭环，不为了未来
  员工模型提前扩张 Schema、权限面和 UI。
