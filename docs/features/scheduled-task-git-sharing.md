# 定时任务通过 Git 随工作空间共享

> 最后更新：2026-08-31
>
> 当前产品事实源：`docs/features/scheduled-tasks.md`
>
> 工程方案：`docs/features/scheduled-task-git-sharing-development-plan.md`

> 架构约束：`docs/architecture.md`、`docs/features/workspace-system.md`、

## 1. 结论

CCLink Studio 应允许用户把一个本地工作空间的定时任务定义显式标记为“随项目共享”，
再通过用户已有的 Git 提交、Push、Clone 和 Pull 流程带到另一台电脑。目标电脑打开包含该
定义的工作空间后可以看到任务，但任务必须默认处于“未在此设备启用”状态；只有用户查看
任务内容、资源范围、计划和输出约定并明确启用后，目标电脑才可以调度它。

本需求只共享**任务定义**，不共享本机执行权。Git 是定义的运输层，不是调度状态 owner，
也不提供云端调度、自动 Pull、运行历史同步或多设备 exactly-once。

核心产品不变量是：

> 定义可以随项目共享；启用、权限和运行事实严格归当前设备。

## 2. 用户可执行的端到端验收

本需求只有在以下真实双工作空间流程通过后，才能宣称用户闭环完成：

1. 用户在 A 电脑打开本地工作空间“甲”。
2. 用户新建定时任务 X，填写任务内容、计划、相对资源和输出约定。
3. 用户选择“随项目共享”，保存任务；Studio 明确提示共享定义可能进入 Git，且不得包含
   密码、Token、Cookie、验证码、恢复码或其他秘密值。
4. 用户在 Git 变更中看见 X 对应的共享定义文件，明确提交并 Push；Studio 不替用户自动
   Pull、Merge 或解决冲突。
5. 用户在 B 电脑通过 Clone/Pull 得到同一个版本的“甲”，再用 Studio 打开它。
6. B 的定时任务侧栏显示 X，并标记“来自项目 · 未在此设备启用”；打开工作空间、读取任务
   文件或恢复 Tab 均不得自动运行 X。
7. B 打开 X，可以查看名称、指令、计划、时区、相对资源和输出约定；界面不显示 A 的绝对
   路径、权限、登录态、下次运行、运行历史或诊断。
8. B 点击“在此设备启用”，确认当前工作空间绑定和权限摘要后，X 才在 B 生成本机
   activation 和下次运行时间。
9. B 的启用、暂停、立即运行和历史变化不修改 A 的本机 activation、权限和运行账本。
10. A、B 都启用 X 时，两台电脑可能分别执行；两端必须明确提示“多设备同时启用可能产生
    重复运行”，不得声称只执行一次。
11. A 修改共享任务并 Push，B Pull 后若本地没有未保存草稿，则重新读取新 revision；若有
    未保存草稿或 Git 冲突，则保留现场并阻止覆盖或运行，给出可操作错误。
12. A 删除共享定义并 Push，B Pull 后不得继续根据孤立 activation 运行旧任务；B 应显示
    “定义已从项目移除”，停用本机 activation，并保留有界的本机历史供用户检查。
13. 用户退出 B 的 Studio 后，X 仍不会由操作系统、后台 Helper 或 Git 触发。

只完成 Schema、文件迁移、Git ignore 调整或单机 mock 测试时，不能声明本需求完成。

## 3. 用户问题与产品价值

当前定时任务在产品上被定义为工作空间一级资源，但任务定义默认进入仓库本地
`.git/info/exclude`。用户在另一台电脑打开同名项目、Git clone 或工作空间副本时，通常看不到
原任务；即使手动复制定义，当前持久化数据还包含 A 的绝对路径，B 的路径不同就可能被判为
无效。

这与“任务属于工作空间”的用户心智冲突。用户会自然区分：

- “甲项目每天生成日报”是项目配置，应当可以随项目携带；
- “是否允许这台电脑执行、使用哪些本机权限”是设备配置，不应静默传播。

该能力对多电脑办公、团队仓库、设备迁移和可审计的项目自动化有直接价值，同时可以复用
用户已有 Git，不要求 CCLink 登录，不把本地能力变成云服务前置条件。

## 4. 需求范围

### 4.1 首版必须提供

- 任务编辑页提供明确的“不随 Git 共享 / 随项目共享”可见性选择。
- 现有任务升级后保持“不随 Git 共享”，不得因版本更新自动进入 Git。
- 共享定义使用可移植格式，不持久化创建电脑的绝对工作空间路径。
- 文件、目录和输出引用只使用工作空间相对路径，并继续执行路径越界校验。
- 共享定义可被普通 Git 状态、提交和 Push 发现，不要求 `git add -f`。
- 目标设备发现共享定义时默认暂停，必须人工启用。
- 本机 activation、权限、运行锁、队列、当前运行、运行历史和内部结果继续留在 `userData`
  或其他明确的本机存储中。
- Git 冲突、损坏定义、重复任务 ID、外部删除和不支持 Schema 必须 fail closed。
- 非 Git 工作空间仍可使用“不随 Git 共享”的定时任务，不因 Git 不可用而降级。
- 用户复制或移动工作空间后，共享定义绑定当前已验证工作空间；复制得到的新工作空间身份
  不继承原设备 activation。

### 4.2 首版明确不做

- 自动 Clone、Pull、Fetch、Merge、Rebase 或 Git 冲突解决。
- 后台文件同步、CCLink 云同步或账号级任务列表。
- A、B 的启用状态、权限确认、登录态、运行历史和诊断同步。
- 多设备选主、分布式锁、心跳、租约或 exactly-once。
- Studio 退出后的系统级调度、设备唤醒或云端代跑。
- 团队权限、任务审批、签名任务包和远程撤销。
- 把普通项目文件中的任意 JSON 自动识别为可执行任务。
- 自动把已有本机任务提交到 Git。

## 5. 用户心智与交互

### 5.1 创建和保存

任务编辑页在保存区域展示：

```text
任务可见性

(●) 不随 Git 共享
    任务定义不会进入项目 Git 变更。

( ) 随项目共享
    任务定义可以被 Git 提交到项目；其他设备看到后仍需手动启用。
```

首版默认选择“不随 Git 共享”。用户切换为“随项目共享”时，保存确认至少展示：

- 任务名称和完整计划摘要；
- 将要共享的相对资源范围；
- 输出位置；
- “定义可能进入远程 Git 仓库”的提示；
- “禁止写入凭证或秘密值”的提示；
- 目标设备默认不会自动执行的说明。

选择共享不等于自动 Commit 或 Push。任务保存成功后，Git 状态出现普通工作区变化，由用户
沿用统一 Git 流程处理。

### 5.2 目标设备发现

B 第一次读取共享任务时，侧栏和 Tab 应显示：

```text
来自项目 · 未在此设备启用

此任务定义由项目文件提供。请检查任务内容、资源范围和计划后再在此设备启用。
多台设备同时启用可能产生重复运行。
```

外来定义不能继承全局 `auto` 权限模式、A 的确认记录或任何“always allow”状态。打开任务、
恢复 Tab、Git Pull、窗口重建和 App 重启都不能替代用户启用动作。

### 5.3 本机任务与共享任务转换

- “不随 Git 共享 → 随项目共享”：保存为新的可移植共享 revision；成功后再移除旧本机定义。
- “随项目共享 → 不随 Git 共享”：先保存本机定义，再删除共享文件；删除会形成 Git 变化，必须
  明确提示其他设备 Pull 后将看不到该定义。
- 转换期间任一步失败都保留至少一个可读取定义，不得产生两个可运行副本。
- 同一 task ID 同时出现在本机和共享位置时视为冲突，禁止调度，不能静默选一份。

## 6. 状态所有权

| 数据                             | 唯一事实源                                    | 是否通过 Git 共享      |
| -------------------------------- | --------------------------------------------- | ---------------------- |
| 共享任务定义                     | 工作空间共享定义文件 + `ScheduledTaskService` | 是                     |
| 本机任务定义                     | 工作空间本机定义文件 + `ScheduledTaskService` | 否                     |
| 当前路径绑定                     | `WorkspaceStateService` 解析后的当前工作空间  | 否，不序列化旧绝对路径 |
| 是否在本机启用                   | `ScheduledTaskService` activation store       | 否                     |
| 权限和可信确认                   | 当前设备权限事实                              | 否                     |
| 当前运行、队列和 timer           | 当前 Studio 主进程                            | 否                     |
| 运行历史和内部结果               | 当前设备 run store                            | 否                     |
| 用户选择另存的普通 Markdown 产物 | 普通工作空间文件                              | 按用户 Git 规则决定    |
| Git index、HEAD、冲突和操作状态  | 本机 Git + `GitWorkspaceService`              | Git 自身事实           |

`ScheduledTaskService` 继续唯一拥有任务定义的解析、保存、启用和运行。Renderer 只显示投影并
发送有界命令。Git 领域只负责报告和操作真实仓库状态，不能解释任务内容或成为第二调度 owner。

## 7. “同一个工作空间”的判定

“同一个”不能按文件夹名称或创建电脑的绝对路径判断。本需求中的同一工作空间表示：目标目录
实际包含通过 Git 或显式文件复制得到的共享任务定义。

共享定义的工作空间归属由它所在且已通过 `WorkspaceStateService` 校验的当前工作空间赋予，
而不是从 JSON 中信任一个绝对路径。稳定 `workspaceId` 仍用于隔离本机 activation 和历史；
不同设备可以为同一份项目文件生成不同本机 workspace identity，这不会阻止读取共享定义，也
不会传播执行权。

以下情况不得误判为同一工作空间：

- 只有文件夹名称相同，但没有共享定义文件；
- 任务文件通过符号链接指向工作空间外；
- 用户把单个任务 JSON 放到另一个未声明位置；
- 远程工作空间或 CCLink RemoteProvider 仅与本地目录同名。

## 8. 安全与隐私不变量

- 来自 Git 的共享定义一律按不可信输入处理，执行前重新通过 runtime schema、大小、枚举、
  路径和未知字段校验。
- 任务定义不得包含密码、Token、Cookie、UserSig、验证码、恢复码、私钥或第三方凭证值。
- 首版不以客户端正则扫描替代用户责任，但共享确认、文档和 Git 敏感文件预检必须覆盖任务
  定义路径；发现明显秘密值时应阻止共享或提交并给出可操作错误。
- 共享任务默认暂停；全局 `auto`、角色、Agent Profile 和旧设备权限不能扩大 scheduled
  allowlist。
- 相对资源在每次保存和运行前重新解析到当前工作空间 realpath，拒绝 `..`、绝对路径、
  符号链接越界和工作空间替换竞态。
- Git 冲突标记、JSON 损坏、未知 Schema、重复 ID 或文件名/内部 ID 不一致时禁止运行。
- 诊断默认只报告 task ID、revision、来源、解析状态和脱敏错误，不复制完整指令正文。
- 共享定义不得扩大 preload API、读取凭证或触发 CCLink 登录。

## 9. 同步、并发与失败语义

### 9.1 Git 不是实时同步

Studio 只保证共享定义是可跟踪的普通 Git 文件。A 的修改只有在用户 Commit/Push，B 再
Clone/Pull 后才可能出现。网络离线、没有 remote、没有 Git 或用户未 Pull 时，B 继续使用本机
已有版本，不显示“已同步”等无法证明的状态。

### 9.2 并发修改

- Tab 草稿固定打开时的 task revision 和内容摘要。
- 外部文件变更后，保存使用 expected revision/摘要；不匹配时拒绝覆盖。
- Git 产生冲突标记时，该任务进入“定义冲突”，停止未来调度。
- 首版不自动三方合并任务 JSON，也不使用 last-write-wins。
- 用户解决 Git 冲突并得到一个合法定义后，服务重新读取；本机 activation 仍由当前设备决定。

### 9.3 外部删除

共享文件消失时，服务必须在下一次对账中：

1. 从可调度定义集合移除该任务；
2. 停止认领未来 occurrence；
3. 将本机 activation 标记为 orphaned/disabled，而不是保留 enabled；
4. 不强杀已经开始的运行；已开始运行按当前固定 revision 收束；
5. 保留有界历史并向用户显示定义已移除；
6. 不因文件重新出现而自动恢复启用。

### 9.4 多设备重复执行

首版每台设备都是独立调度器。两台设备都显式启用同一任务时，允许分别执行。任务 ID、
occurrence key 和 revision 只能在单设备内去重，不能被描述为全局唯一。

若未来要求多设备只执行一次，必须另立云端或对等协调需求，明确在线 owner、租约、网络分区、
时钟偏差、离线恢复、最终一致性和服务端权限；不得在本需求中用 Git lock 文件伪装分布式锁。

## 10. 可观测性与诊断

诊断至少包含：

- workspace identity 和 canonical path 的脱敏摘要；
- task ID、持久化 schemaVersion、revision、定义来源（local/shared）；
- 共享文件是否存在、是否被 Git ignore、是否 tracked、是否 unmerged；
- parse/migration/rebind 状态和结构化错误码；
- 本机 activation 是否存在、enabled/disabled/orphaned 和来源设备；
- 最近一次外部变更检测时间；
- `systemScheduler=none`；
- 不包含任务完整指令、文件正文、remote 凭证或绝对路径全集。

Git 不可用、仓库不存在或 Git 状态读取失败只影响共享诊断和 Git 操作，不影响本机任务创建、
编辑、启用和运行。

## 11. 产品文案

统一使用以下术语：

| 文案           | 含义                                                       |
| -------------- | ---------------------------------------------------------- |
| 不随 Git 共享  | 定义不进入项目 Git 共享范围                                |
| 随项目共享     | 定义可以由用户通过 Git 或文件复制带到其他设备              |
| 来自项目       | 当前定义来自工作空间共享文件                               |
| 未在此设备启用 | 当前设备没有有效 activation，不会自动运行                  |
| 定义冲突       | 文件损坏、重复 ID、Git conflict 或并发版本不一致，禁止运行 |

禁止使用“云同步”“自动同步”“团队任务”“全局任务”“只执行一次”等超出首版事实的文案。

## 12. 产品完成门禁

### 12.1 用户功能进度

- [ ] A 可以把一个本机任务显式转换为随项目共享，并在真实 Git 变更中看见定义。
- [ ] B Clone/Pull 后打开真实工作空间可以看见任务，且默认不启用。
- [ ] B 明确启用后可以立即运行和按计划运行，A 的 activation 与历史不受影响。
- [ ] A 修改、删除以及 A/B 并发修改在 B 有明确且安全的结果。
- [ ] 两台设备同时启用时有重复执行提示，不伪造 exactly-once。
- [ ] 非 Git、Git 离线、Studio 未登录和 CCLink 故障时，本机任务仍完整可用。

### 12.2 工程准备度

- [ ] 可移植持久化 Schema、v1 兼容和迁移门禁通过。
- [ ] managed Git exclude 迁移只修改 Studio 自有规则，不覆盖用户规则。
- [ ] activation/history/results/credentials 永远不进入共享候选文件。
- [ ] 冲突、损坏、外部删除、符号链接越界和保存竞态 fail closed。
- [ ] `ScheduledTaskService` 与 `GitWorkspaceService` 状态所有权没有重叠。
- [ ] 受影响测试、真实 Git smoke 和双工作空间 Electron smoke 通过。
- [ ] 真人在两台独立电脑或等价隔离用户目录上完成第 2 节全部验收并记录结果。

## 13. 拷问结论

- 如果实现只是删除 `.git/info/exclude`，但定义仍保存绝对路径，需求未完成。
- 如果 B 看见任务后自动启用，安全边界失败。
- 如果为了“同步”把 activation 或运行历史写进工作空间，状态所有权失败。
- 如果 Studio 自动 Pull/Merge，需求已扩张成 Git 同步系统，应立即止损并另立项目。
- 如果用 Git 文件锁声称多设备只执行一次，结论不可信。
- 如果现有任务在升级后未经用户确认就进入 Git，隐私和兼容性失败。
- 如果只有单机两个文件夹测试，没有隔离 userData、不同绝对路径和真实 Git 往返，不能证明
  跨设备闭环。
