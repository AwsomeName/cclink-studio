# 公司经营账与眼镜研发成本管理讨论稿

更新日期：2026-10-09。状态：需求与方案讨论，未实现；存储和面板方案尚未定案。

当前讨论位置：用户在了解专业软件核心功能后要求重新设计。最新提案见 [AI 账目助理核心产品设计](company-accounts-product-design.md)。本文件保留前期讨论与存储候选，旧页面草稿继续暂存；尚未定案或进入实现。

## 目标与边界

让用户看清公司实际收支、眼镜研发采购与打样等支出，并能从汇总追溯到原始证据。先管理内部经营账；正式财税账的科目、入账和申报口径由财务人员确认，经营分类不能直接替代正式入账结论。

本轮只记录方案，不修改功能代码。后续在账目范围、存储和界面达成共识后，再讨论运营。

## 用户验收闭环

1. 导入一个月的账单及订单、合同、发票、收据或付款截图，保留原文件并显示来源，标出疑似重复。
2. 核对金额、交易对象、类别、研发项目及关联凭证；对缺项、退款、拆分和无法归属的记录保留明确待处理状态。
3. 用户查看证据并确认；保存确认人、时间和所确认的记录版本。AI 建议、识别结果和自述不得直接成为已确认账目。
4. 按年、月、周、日和自定义期间查看实际收支和指定研发项目的费用明细，能下钻到原始记录与凭证；待确认金额独立显示，不混入已确认汇总。切换期间或筛选条件时，图表、合计、明细与导出口径一致。
5. 导出与界面相同口径的明细、汇总及凭证索引，包含期间和确认状态；备份后能恢复记录、附件及历史。

## 核心功能和逻辑

| 功能 | 回答的问题 | 范围 |
| --- | --- | --- |
| 收支记录 | 实际收到或付出多少现金 | 首个闭环候选 |
| 采购记录 | 买了什么、向谁买、总价多少 | 首版深度待讨论 |
| 凭证管理 | 这笔记录有什么证据 | 首个闭环候选 |
| 分类与核对 | 是否重复、金额是否一致、属于哪个项目 | 首个闭环候选 |
| 人工确认 | 谁检查过哪一版记录 | 必须保留 |
| 项目费用分析 | 眼镜型号或研发批次花了多少 | 首个闭环候选，口径待定 |
| 报表中心与导出 | 每年、每月、每周、每天及指定期间的收付、分类与趋势 | 首个闭环候选 |
| 报销 | 对话或表单提交、人工审批、退回、真实付款登记 | 已纳入产品设计，首版实施深度待定 |
| 库存 | 器件收到、领用及剩余数量 | 是否首版需要，待确认 |
| 应收应付 | 谁欠公司钱、公司欠谁钱 | 是否首版需要，待确认 |

付款、发票和收货是不同事实，必须关联但不能互相替代。例如采购 100 个传感器总价 5,000 元，先付 2,000 元，眼镜 A 领用 20 个：现金支出是 2,000 元，未付款是 3,000 元，剩余库存是 80 个。项目成本如何计入，需要先确定领用、服务验收和分摊规则；不能把付款额自动当作项目成本。

一笔业务可能有多次付款和多个凭证，一笔付款也可能覆盖多个业务或项目。导入数据、业务记录和汇总之间应保留可追溯关联，避免每份截图或发票都生成一笔新支出。

## 证据与记录保护

- 原始账单和凭证保留原件；识别文字、摘要和 AI 分类作为附加资料。候选设计使用稳定编号与文件校验值辅助关联和检测变化。
- 状态至少区分待核对、待确认、已确认；存在异常时记录原因和允许的下一步。无凭证是否允许确认及如何标记，需与用户讨论。
- 确认记录绑定具体版本，包含操作者、时间和确认内容。修改已确认金额、项目或关键关联后应重新确认。
- 更正保留修改前后内容、操作者、时间和原因；不能静默覆盖已确认历史。避免直接删除已确认账目，采用作废或更正并保留关联历史的候选方式。
- 备份覆盖账目、原文件、关联、确认记录和修改历史；存放到独立位置，并实际验证恢复。具体频率、访问权限和是否加密尚待决定，备份不能只复制一个正在写入的数据文件。
- AI 可以识别、分类、匹配、提示疑点和解释汇总；确认和关键更正由用户在受控入口完成，不能由 Agent 直接写文件绕过。

## 存储候选方案

用户最新方向：复用普通项目／文件夹对应的既有工作空间，通过专门的类型说明文档或初始化配置描述账目用途、规则和 AI 工作方式；不新增独立的财务工作空间状态类型。账目工作台是该普通工作空间可启用的能力。

用户提出“先不用目录”。暂按不强制创建额外财务目录树理解，待确认是否也指暂不选择数据落盘目录。本轮不创建账目工作空间或目录。说明文档负责解释规则，不能代替结构化账目事实、确认记录或权限检查。

眼镜 A/B 等研发项目是账目内部的成本归属，不另建一套 Studio 项目状态。

候选目录职责：原始资料、结构化账目、导出报表、备份说明。真实账目存放在用户选择的私人目录，不进入 Studio 源码仓库，不默认 Git 提交或云同步。具体文件命名和格式未定。

目录与数据库不是二选一：目录提供边界与原文件容器，结构化账目仍需要可靠存储。

| 方案 | 优点 | 需解决的问题 |
| --- | --- | --- |
| 工作空间内 CSV/JSON 等文件 | 容易查看、迁移和使用外部工具 | 多记录修改一致性、重复导入、历史追踪、并发写入与恢复需要专门设计；不宜只靠 Agent 改表 |
| 工作空间内独立 SQLite 文件 | 候选方案可集中处理关联、查询与事务；账目随目录迁移 | 需要受控写入、格式迁移、完整备份和导出；用户直接改库不能绕过确认 |
| 外部财务系统作为事实源 | 可复用已有会计与多人协作能力 | 取决于现有系统、接口、权限和离线要求；不能假设已经可接入 |

建议避免把公司账目塞进 Studio 全局内部状态库。是否完全不用数据库，仍需确认：用户反对的是“数据藏在应用里”，还是任何数据库文件？尚未选型，也未审计当前内部数据库实现。

第一阶段候选边界是本地单人使用，不支持多人同时写入或通过同步盘合并数据库。多人协作需求会直接影响存储决策，应在实现前确认。

## AI 代理记账与主动提醒

用户希望 AI 承担日常代理记账并主动提醒，减少每年人工或服务费用。这是产品目标；尚未确认具体要减少的费用、现有服务范围或可替代程度，不能承诺替代全部正式财税服务。

候选工作方式：用户提供账单和凭证，AI 整理并匹配已有业务，提出分类和研发项目归属，标出缺失、疑似重复及金额不一致；用户查看一份待确认清单并确认；系统生成已确认汇总和供会计使用的导出。AI 可以自动准备待确认记录，不能自动确认、付款或提交申报。

工作空间说明／初始化配置可以描述用途、分类规则、研发项目、允许的数据来源及提醒偏好。规则与 AI 建议可修订，但不得借修改说明文档绕过账目服务的确认与追踪要求。

提醒候选范围：

- 定期提醒补交账单、检查待确认清单和完成月度核对。
- 针对有证据的缺凭证、重复交易、金额不一致及备份失败提醒。
- 启用应收应付或报销后，按已登记的到期日提醒付款、收款或未报销事项。

提醒需可处理、可暂缓、可关闭并避免重复轰炸；事实未变化时不重复通知。截止日期来自用户确认的规则或已登记记录，AI 不能猜测欠款或法定期限。涉及正式财税期限的能力另行核实和设计。

主动提醒需要明确应用关闭、电脑睡眠、离线或数据未更新时的行为。本地执行不能承诺关机后按时送达；恢复后应展示遗漏事项和数据更新时间。当前只讨论能力，没有创建自动化或提醒任务。

验收候选：用一批真实账单验证 AI 准备记录的正确性和人工处理时间；用户确认后可追溯原件并导出；模拟遗漏凭证及到期事项验证提醒、暂缓和去重；从备份恢复。节省费用需对比现有服务成本、新增 AI 使用成本和人工核对时间，不能仅凭自动生成表格宣称实现。

## 专业软件调研后的页面方案

在该工作空间中打开账目专用工作台标签页，复用既有 Workspace、Tab、文件预览和 Agent 面板；不另建一套工作空间或全局财务侧栏状态。

- 报表中心作为主要查看入口：年、月、周、日和自定义期间，收支合计、结余、趋势、分类、项目和账户筛选及明细下钻。现金净流入不等于利润；账户互转不是经营收入，借款和出资等另行分类。未导入期间显示资料不完整，不能当零。
- 项目账：列表与项目详情，按眼镜型号和批次归集采购、器件、打样、服务和报销；比较预算与已确认业务费用，另列实际付款和待付款。预算先由用户设定，成本纳入规则先确认。
- 报销申请：对话输入“我替眼镜 A 买了器件 800 元”，附资料后由 AI 准备草稿。结构化表单包含申请人、发生日期、项目、用途、费用明细、垫付方式、附件与审批人；用户检查后提交。
- 审批与付款：草稿、待审批、退回、已批准待付款、部分付款、已付款或作废分别记录。人工审批意见、确认和真实付款凭证保留，AI 不批准或执行转账。角色由可信应用身份提供，不能只把 AI 文本中的名字当审批人；多人在线提交和身份方案另行设计。
- 流水与凭证：原始资料导入、重复检测、业务匹配、异常处理、确认和更正。银行报销付款匹配已有申请，结清待付款而不新增第二笔业务费用。只知道支出用途时不能直接宣称正式会计入账。
- 导出与交接：根据当前报表筛选准备明细和凭证索引，跟踪交给代账和实际返回结果。备份、恢复、更正追踪和提醒规则作为辅助入口，不占据产品主线。

选择一笔记录时显示原始凭证和关联信息，再执行确认。报表和申请单是核心交互，不只呈现待办或聊天。基本报销已纳入设计；多级审批、多人在线提交、支付集成、库存和完整欠款功能的范围待决。

两种口径必须分开：员工垫付 800 元后，已确认业务费用可显示 800 元、公司已付 0 元、待报销 800 元；公司实际归还后，公司现金支出增加 800 元，但项目业务费用不能再增加一次。待确认、退回和作废的单据不能混入已确认费用；对部分付款、退款和跨项目分摊保留明细关联。

此次调研基于官方公开产品页面和操作文档，未登录软件实际试用。多周期、项目、报销流程有来源依据；对话生成结构化单据是 Studio 的设计建议，不声称所有参考软件都有相同交互。

## 实现前必须明确的约束

候选能力边界为本地内部经营账，不执行付款、报税或自动正式入账。账目服务作为唯一写入与确认所有者，UI 和 Agent 只提交受校验的请求；renderer 不直接读写本地文件。遵守架构宪法的契约、串行原子持久化、迁移恢复和对称生命周期要求。

账目模块失败不得阻断 Studio 其他本地能力。工作空间切换需要释放旧监听和任务，写入失败必须明确提示且不能显示已确认成功。访问限制到用户选定的账目范围；诊断避免泄露金额明细、账号和原始凭证正文。

实现前还需明确导入格式、权限、异常处理、备份恢复与验证方式。工程门禁与真实产品验收分别报告；只有完成上述真实应用闭环后才可声明能力交付。

## 待回答的问题

1. 现有付款渠道、账单格式、凭证位置和历史数据范围是什么？
2. 谁登记、核对和确认，单人还是多人？
3. 最急的是看清花钱，还是器件库存、员工报销和供应商欠款？
4. 是否已有会计或代账软件，导出需要对接什么？
5. 希望独立账目目录放在哪里，允许什么备份位置？“不用内置数据库”的具体顾虑是什么？
