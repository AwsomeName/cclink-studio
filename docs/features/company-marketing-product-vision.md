## 一句话

**一个人经营的公司的销售与售后助理。** 它把研发和真实使用中值得讲的事变成内容，保证每个想买的人、每个买了遇到问题的人都得到及时、正确的回应，并告诉你什么带来了咨询和订单、什么在反复出问题。你始终是发声和做决定的人，它做跑腿的事。

本文从产品目的出发说清理想形态与用户期望，再对照现有能力说明可以复用什么、缺什么。实现方案另行编写。

## 在公司项目里的位置

公司项目要支撑日常经营。它有四项业务功能，共用一个公司首页：

| 功能       | 回答的问题                                       | 事实来源                                         |
| ---------- | ------------------------------------------------ | ------------------------------------------------ |
| 业务项目   | 每件业务的目标、销量、库存和进展                 | 公司领域：业务项目与关联                         |
| 公司账目   | 这个月的账是否清楚、各业务赚了多少花了多少       | 公司账目：导入、核对、月度汇总、导出给代账、备份 |
| 推广       | 今天能讲什么、谁批准了、发出去带来了什么         | 本文定义；发布执行复用文章发布与网页事务         |
| 客户与售后 | 谁想买、谁买了有问题、谁在等我、哪些问题反复出现 | 本文定义                                         |

- **公司首页**把需要你处理的事放在一起：售后待回复、退款待你同意、意向客户待回复、推广待批准、账号需重新登录、流水待核对。每条写明去哪里处理，点一下直达原功能。
- **推广**和**客户与售后**是侧栏的两项，取代原“运营内容”。首页底部“推广与客户”块和待办按钮都直达这两页。
- **订单事实属于网店。** 下单、发货、退款数从网店后台读取并标明读取时间；收入以账目里已确认的结算流水为准。两者对不上时（结算延迟、退款未到账）首页写明原因，不自行推算。
- **账目与推广、售后相连的地方只有钱。** 推广费用、售后换件和运费、退款照常作为流水导入账目、人工确认，并归到对应业务项目；推广和售后页面只读取已确认金额，不另记一套。
- 发布、评论和消息读取、回复的执行能力是全 Studio 共用的；公司项目按业务把它们组织起来。

## 用户与阶段

**谁在用：** 做 AR 眼镜的创始人，产品已上市，一个人或很小的团队，没有专职客服和市场。

**处在什么阶段：** 直接销售，已有订单和在用的买家。这个阶段的目标：

1. **把产品卖给需要它的人**：让关心智能眼镜、通勤和办公场景、近视适配的人看到真实、准确的介绍，并找到购买入口。
2. **把买了的人服务好**：问题得到快速、正确的回应；该换的换、该退的退；反复出现的问题回到研发。

**这个阶段怎么算有效：**

| 指标                 | 说明                                                       |
| -------------------- | ---------------------------------------------------------- |
| 售后等待时间         | 买家的问题多久得到第一次回应、多久解决；超过承诺时限要显眼 |
| 意向客户等待时间     | 问价、问适配、企业采购的消息多久得到回应                   |
| 咨询与订单来源       | 哪篇内容、哪个平台带来了咨询和下单（能归因的才显示）       |
| 退货率与退货原因     | 按原因分类，不只看比例                                     |
| 反复出现的问题       | 例如“镜腿松动”“App 连不上”，转给二代研发或改说明书         |
| 每周花在这些上的时间 | 应该明显下降                                               |

关注者和阅读数只作次要参考；读不到的写“未获取”。

## 用户真正要做的五件事

1. **不从白纸开始讲产品。** 研发记录、真实使用反馈（经买家同意）、已修复的问题，本身就是素材。
2. **在买家所在的地方，用平台自己的形式出现。** 同一件事写成知乎长文、小红书图文，不是同一段文字贴八次。
3. **不漏掉任何人。** 想买的人、企业询价、买了遇到问题的人、要退货的人。漏掉一个售后问题，比少发一篇文章代价更大。
4. **回复得快、像自己、事实正确。** 用你的名义说错续航、保修期或退款规则，比不回复更糟。
5. **知道什么有效、什么在出问题。** 哪些内容带来了咨询和订单；买家反复问什么、反复坏什么，应该回到产品和说明书，而不只是下一篇内容。

## 理想的一天与一周（AR 眼镜一代在售）

- **每天早上，打开公司首页。** 看到：3 个售后问题待回复（最久等了 20 小时）、1 笔退货退款待你同意、2 位意向客户待回复（其中一家企业问 50 副的报价）、1 篇推广待批准、小红书账号需要重新登录、23 条流水待核对。
- **售后。** 每个工单显示买家、订单号、购买天数、问题和来往记录。助理按保修政策和使用说明起草回复，例如镜腿松动“在保修期内，寄回换件、运费我们承担”。你批准后发送，并在平台上核验已发出。
- **退款。** 助理整理订单、原因和政策依据；打开网店后台该订单页面，由你本人点击同意。Studio 只读回订单状态，退款流水进入账目后由你选择冲减收入还是记为支出。
- **意向客户。** 问价格、问近视能不能用、企业采购，按意向分好。事实表里有答案的问题助理起草回复；价格、优惠和企业报价只起草，由你决定。
- **推广。** 助理从研发和售后里找出可以讲的事，例如“镜腿结构改版通过测试”（尚未验证的改进不对外宣传）、“一位买家通勤一个月的体验”（需对方同意引用）。每个平台一版，对照产品事实表核对，冲突未处理前不能批准；你按账号逐个批准，发布后读回公开结果才算“已发布”。
- **周五，什么有效。** 本周哪篇内容带来了几个咨询和订单、退货原因分布、最常被问和最常坏的三件事，以及哪些已转给二代研发。

## 用户期望与产品承诺

| 用户期望（常常不说出口） | 产品承诺                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| 真正省时间               | 一个首页代替网店后台、几个平台和聊天工具来回切换；每周花费的时间可以看到并下降               |
| 像我，不让我难堪         | 从我写过的回复学语气；不编造参数、价格、保修承诺或发货时间                                   |
| 以我名义说的话由我控制   | 信任逐级放开、随时收回（见下节）；发出的每条内容都有记录                                     |
| 钱的事只有我能动         | 退款、改价、优惠、企业报价由我本人处理；Studio 只起草、只读回结果                            |
| 不让账号被封             | 遵守平台规则，按人的节奏操作；不刷量、不群发、不制造虚假互动或评价                           |
| 不漏掉任何人             | 售后和意向客户立即出现在首页，显示等待时长；超过承诺时限的排在最前                           |
| 数字诚实                 | 订单数标明来自网店和读取时间；收入只算已确认流水；读不到写“未获取”，不写 0 也不估算          |
| 买家的资料安全           | 对话、订单、地址和联系方式只保存在本机，不进入 Git、诊断或项目共享配置；只使用售后需要的信息 |
| 几乎不用配置             | 账号登录一次即可；保修政策、使用说明和产品事实表可以从已有资料起草，再由我确认               |

## 信任阶梯

每类动作、每个渠道单独设置，可以随时降级，所有动作可审计：

| 级别 | 含义                                 | 默认                                                 |
| ---- | ------------------------------------ | ---------------------------------------------------- |
| 0    | 只起草，不在平台上做任何事           | 价格、优惠、企业报价、退款、投诉与纠纷、媒体与合作   |
| 1    | 我逐条批准后执行                     | 发布内容、回复评论和私信、回复售后问题               |
| 2    | 我批准一条规则，规则内的动作自动执行 | 可选：物流查询、事实表与使用说明里已有答案的常见问题 |
| 3    | 在规则内自主执行，事后汇报           | 首版不开放                                           |

这与 [ADR 0016](../decisions/0016-agent-web-account-execution.md) 一致：用户看到目标网站、账号、内容快照和预期结果后点击开始，就授权与快照一致的常规动作；验证码、扫码、风控、法律或版权声明、付款与退款、批量或范围扩大、未知页面状态一律交给用户。第 2 级规则也不能越过这些卡点，并且每次公开发布仍需对具体账号和文章授权。

## 产品事实表与售后口径

最容易出错的是事实：续航、重量、近视适配范围、保修期、退换规则、发货时间。公司项目里保留由用户确认的两份资料：

- **产品事实表**：每条事实有内容、确认时间和来源（测试报告、设计文件）。
- **售后口径**：保修期、换件流程、退款条件和记账方式、运费承担。

规则：

- 起草内容和回复只能引用事实表、售后口径、使用说明或研发资料；冲突或没有答案时标为待确认。
- 事实或口径更新后，列出引用过旧内容、尚未发布的草稿和待发送的回复。
- 已发布内容不自动修改；需要更正时由用户决定。

## 客户记录

“人”是客户与售后的核心对象。每个人的记录从对话和订单中自动形成，不需要手填表：

- 在哪个平台或网店出现；想要什么（购买咨询、企业采购、售后问题、退货退款、其他）；关联的订单。
- 当前状态：新消息、已回复、处理中（换件寄回、等待买家）、已解决、已结束。
- 下一步和等待时长；同一个人在不同平台出现时，由用户确认是否合并，不按昵称猜测。
- 售后问题按原因归类，同类问题累计到一定数量时提示是否转给研发。

## 不做什么

- 不做群发、刷量、刷评价、自动关注或虚假互动。
- 不做以点赞和浏览量为中心的数据面板。
- 不做需要手工录入的客户管理表单。
- 不代替用户退款、改价、发优惠或报价；不在 Studio 里收付款。
- 不做自动回复（第 3 级）、广告投放和自建商城。
- 不新建账号登录体系，不读取或保存平台密码、Cookie。

## 分阶段验证

每一阶段以用户在真实应用里能完成的动作为准；只有前一阶段在真实平台上通过，才进入下一阶段。公司内部排在这些之前的是[公司账目真实月份验收](../project-memo.md)。

1. **一篇推广从批准到已发布。** 从眼镜研发的一条真实进展起草知乎和小红书两版，事实表核对通过，逐账号批准，实际发布并核验公开结果，文末带购买入口。大部分能力已经存在；需要用户对具体账号和文章授权。
2. **回复一位意向客户。** 读取已发布内容下的评论或私信，识别出购买咨询，起草回复，批准后发送并在平台上核验已发出。
3. **处理一个售后问题。** 从网店读取一张真实售后单或客服消息，关联订单，按售后口径起草回复，批准后发送并核验；涉及退款时打开网店后台由用户本人确认，Studio 读回状态，退款流水在账目中确认并归属业务。

## 待用户决定

1. **网店在哪个平台？** 它决定订单、售后单和客服消息能否通过账号环境读取。
2. **推广主要在哪两三个平台？** 当前设想以知乎（技术读者）和小红书（佩戴体验）为主。
3. **售后统一口径。** 保修期、换件流程、退款条件、运费承担、退款记账方式。
4. **谁可以代表公司回复？** 是否只有你本人；价格、优惠、企业报价的统一口径。
5. **公开研发细节的边界。** 哪些进展可以讲，哪些（供应商、成本、未申请的专利、未验证的改进）不能讲。
