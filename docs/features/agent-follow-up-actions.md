# Agent 后续消息操作产品设计

> 2026-11-06（Asia/Shanghai）。用户已确认交互方案；本文保存产品规则、实现边界与验收要求。
> 本地 Claude Code 的“补充当前任务”和“停止并执行这条”已实现，并通过真实 Electron + Runtime 的核心动作验收。远程和 Codex ACP 的这两项操作保持禁用。

用户现在可在本地 Claude Code 会话中选择排队、补充当前任务或停止后执行新消息。补充首批只支持纯文字；停止后执行保留并暂停原队列。真实运行、截图与尚未覆盖的场景见[后续消息操作验收记录](../testing/agent-follow-up-actions.md)。远程队列已有代码和界面夹具验证，真实远端执行继续按用户安排留待实际使用反馈。

现有队列、恢复与远程限制仍以[会话待发送消息队列](agent-message-queue.md)为准，实际通过范围见[队列验收记录](../testing/agent-message-queue.md)。本设计扩展后续消息操作，不把效果图中的模拟反馈当作实现证据。

## 用户可执行的验收动作

在真实 Studio 的同一个本地 Claude Code 会话中，启动任务 A，执行期间排入 B、C。用隔离工作空间和只读任务验证，运行记录必须能够关联原任务、新任务和补充消息。

| 用户动作                                            | 应看到的结果                                                   | 必须核对的执行事实                                                                 |
| --------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 执行中输入 D，按 Enter                              | D 出现在 B、C 后面，输入框可继续输入                           | A 结束后按 B、C、D 顺序执行，同一会话不并行                                        |
| 执行 A 时输入“后续回答使用中文”，点击“补充当前任务” | 历史中出现属于 A 的补充消息及接收状态；B、C 顺序与暂停状态不变 | A 的后续响应使用这条补充；没有通过新建 Studio Run 或中止重发伪装补充               |
| A 执行期间点击“停止”                                | 先显示“正在停止”，收到确认后显示“已停止”；B、C 保留且暂停      | 目标 A 的 Runtime 执行及受其管理的在途工具已结束；不能以按钮点击或发送回执代替终态 |
| 输入 D，点击“停止并执行这条”                        | A 正在停止时 D 显示为等待停止确认；确认后执行 D，B、C 仍暂停   | D 只启动一次，启动时间晚于 A 的确认退出；A 的迟到事件不能覆盖 D                    |
| 点击“继续队列”                                      | 若 D 还在执行，B 等 D 结束；若已空闲，则执行 B，再执行 C       | 显式继续才解除暂停，D 的成功或重连不能自行解除暂停                                 |
| 原任务即将结束时点击补充，或停止过程发生错误        | 明确显示未接收、失败或状态未确认，保留消息内容                 | 不把补充送入下一任务，不自动重试，不在未知状态下启动 D                             |
| 切换会话、收起面板，再返回                          | 消息和操作状态仍属于原会话；停止确认不串到当前打开的会话       | 订阅不依赖面板挂载；工作空间、会话、Run 三者均匹配                                 |
| 在 CCLink 远程会话打开同一操作菜单                  | 排队可用；缺少能力的操作禁用并给出原因；停止仍叫“停止等待”     | 不把 untracked、断流或 session 列表 idle 当作远端取消成功                          |

验收应在右侧聊天区和 Workbench 会话视图重复核心动作，检查浅色、深色、窄面板、中文输入法 Enter、权限等待和重启恢复。用户已明确暂不登录 CCLink；真实远程执行继续标记为待验收，不阻塞本地实现。

## 已确认的输入框和操作语义

输入框只有一个。运行时保留独立的“停止”按钮，主发送按钮为“加入队列”，旁边的下拉菜单直接对当前草稿执行另外两种操作，不永久改变默认发送方式。

| 操作           | 含义                                     | 对已有队列的影响                       |
| -------------- | ---------------------------------------- | -------------------------------------- |
| 发送           | 空闲且没有待发送或暂停状态时，启动新一轮 | 不越过已有待发送消息                   |
| 加入队列       | 把当前草稿快照追加到队尾                 | 按顺序等待；不改变既有暂停状态         |
| 补充当前任务   | 给指定的正在执行任务增加信息或纠正方向   | 不插入普通队列，不改变其顺序和暂停状态 |
| 停止           | 请求结束指定的当前任务                   | 保留并暂停队列；确认停止后也不自动继续 |
| 停止并执行这条 | 请求停止当前任务，确认后优先启动当前草稿 | 原队列保留、暂停，由用户决定何时继续   |

- Enter 执行主按钮：忙时加入队列，完全空闲时发送。队列已暂停或仍有待发送项时，Enter 继续入队，不偷偷插队。
- Shift+Enter 换行。Cmd+Enter（macOS）或 Ctrl+Enter（其他平台）在能力可用时补充当前任务；能力不支持时不退化为普通发送。快捷键应接入现有统一命令和作用域路由。
- 下拉菜单只显示操作和简短结果说明；不展示协议名、SDK 参数或内部 run ID。
- 不依据消息中的“等等”“先别做”等文字猜测取消或插队。紧急停止由明确操作触发，消息正文仍作为用户内容处理。
- 空草稿只禁用发送类操作，停止保持可用。中文输入法确认候选字时不提交。

例子：“同时兼容 Windows”适合补充；“做完后补测试”适合排队；“先别修改，只分析原因”需要尽快停止原路线时，使用“停止并执行这条”。补充不保证撤销已经开始的工具调用。

## 接收状态与历史展示

补充消息显示在原任务的历史中，以“补充当前任务”区分普通新一轮消息，保留正文和可审计的关联关系。

1. 请求提交后显示“待接收”。只有能够证明目标 Runtime 接收了该消息的事件或回执，才显示“已接收”；仅写入本地缓冲或 IPC 返回成功不够。
2. “已接收”只表示接收，不表示模型已经采纳、不表示当前工具已经停止。行为是否改变，仍应观察后续执行。
3. 明确拒绝显示“发送失败”并保留内容。传输结果不明显示“接收状态未确认”，保留可复制/恢复的内容，不自动重发以免重复。
4. 发送时固定目标会话和 Run；目标已经结束或替换时，显示“原任务已结束，补充未发送”。不能落到下一轮任务。
5. 首批每个 Run 同时只允许一条未确认补充，确认后可继续补充。待确认期间仍可编辑新草稿和加入普通队列，回执不得清空后写内容。

## 停止后切换任务

“停止并执行这条”是一个明确操作，点击本身已表达切换意图，不再机械弹出第二次确认。原有工具权限、敏感操作和有界任务授权仍有效。

1. 操作受理时，固定原会话、工作空间、Run 和新消息内容/附件快照，暂停普通队列。
2. 原任务进入“正在停止”；新消息显示“等待停止确认”，禁止重复派发。后写的新草稿独立保留。
3. 只有原 Run 的取消终态及 Runtime 退出条件满足，才允许通过原发送入口启动新 Run。取消回执 `accepted` 不能放行。
4. 已开始取消时，旧任务迟到的完成/错误事件不得绕过取消 owner。若点击时旧任务已自然结束，保留消息并提示用户重新发送，不把过期的切换意图自动执行。
5. 停止失败、超时、进程断开或终态无法核实时，不启动新任务，不自动重试。内容留在原会话的待处理状态，普通队列继续暂停。
6. 切换到同一工作空间中的其他会话或收起面板不取消已受理的操作，目标始终固定；切换工作空间、归档、账号变化或执行配置变化时，未启动的新任务暂停，返回后由用户恢复。
7. 关闭应用或崩溃后不自动续发切换消息。本地按现有草稿/队列恢复规则保留可恢复内容并暂停；不能承诺跨崩溃恰好一次。远程仍遵守进程内状态限制。

停止不会回滚已经写入的文件或已经完成的外部操作。独立后台进程或已提交的外部任务不能仅凭前台 Run 结束声称取消，界面和诊断须保留实际未确认范围。

## 首批实施细则

以下使用保守默认值，不需要为了开始本地实现再次确认整套方案。

- **补充先支持纯文字。** 沿用当前 Run 已确认的资源、角色、工作空间和权限，不切换运行环境。草稿含图片或新增 `@` 资源时禁用补充并说明原因；普通排队和停止后新任务继续使用现有附件能力。不得静默丢弃附件后仅发送文字。
- **压缩与取消期间不接受补充。** 普通队列仍可接收后续消息；不能把压缩过程当作可补充的用户任务。
- **等待权限不代表允许执行。** 补充可以增加说明，但不能自动批准或改写已展示的工具请求；需要让旧工具失效时应停止任务，既有权限 owner 处理挂起请求。
- **不增加回滚、队列拖拽排序、全局发送偏好或并行执行。** 编辑后重排到队尾、容量、附件恢复和队列暂停保持既有规则。
- **能力必须按后端证明。** 菜单可共用，能力判断不能只看“本地”或“Codex”名称；未知或未验证时禁用并解释，不伪装成另一个操作。

## 能力边界与实现证据

核对日期为 2026-11-06。界面按实际后端能力显示可用状态，不能用产品名称替代能力证明。

| 入口                        | 当前实现                                                                                                                                                         | 放行范围                                                                                                                  |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 本地 Claude Code 补充       | 同一 SDK query 的可追加输入；目标 Run、消息 UUID 和有界文字经统一 IPC 校验；仅 Runtime 声明 `msg_lifecycle_v1` 且对应 `command_lifecycle.started` 到达才确认接收 | 真实长工具执行期间补充后得到新要求的回复，Studio 仍只有一个 Run；纯文字、原上下文、每轮最多 50 次、同时最多一条未确认输入 |
| 本地 Claude Code 停止后执行 | 新消息复用原会话队列 owner；仅目标 Run 的 cancelled 终态放行；`abort()` 等待 SDK 读循环及 Studio 管理工具收尾                                                    | 真实 Bash 等待期间停止，观察到 cancelling → cancelled → 新 Run running；原队列和后写草稿保留                              |
| 本地 Codex ACP              | 当前 `session/cancel` 通知没有原 prompt cancelled 响应的完整确认链                                                                                               | 两项新增操作禁用并解释；普通发送、排队和已有停止入口保持原语义                                                            |
| CCLink 远程                 | `stopTrackingAgentRun` 只停止 Studio 跟踪，并不取消远端工作                                                                                                      | 保留队列与“停止等待”；两项新增操作禁用，不修改云端或外部 Agent runtime                                                    |

补充使用 SDK 的 `priority: next` 在当前查询的后续处理点接收，不保证即时打断在途工具。120 秒未等到接收证明时显示“接收状态未确认”，保留正文且不自动重发；如果之后收到同一 Run 的真实接收事件，历史会更新为“已接收”；该状态仍不等同于模型已采纳。原任务先结束且补充尚未开始时关闭该 query，防止未跟踪的新轮次继续执行。取消/切换等待为 30 秒，超时后必须人工检查并继续。

## 架构与实现约束

| 约束           | 实施要求                                                                                                                                                              |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 能力边界       | 新增的是后续消息操作，普通队列继续由 Studio 调度；不把待发送队列整体灌入 SDK，不新增通用调度平台                                                                      |
| 状态所有者     | Runtime/AgentBridge 拥有执行、取消、补充接收事实；现有会话 store 拥有草稿、队列及未执行的切换意图。UI 只持菜单展开等瞬时状态                                          |
| 身份与契约     | 使用会话、工作空间、目标 Run、消息 ID 定位；新增能力/补充命令沿 shared contract 和 schema 接入。主进程核验有效目标、权限、内容大小与幂等，不增加第二套 IPC 字符串声明 |
| 生命周期       | 接收/退出监听随既有 bootstrap 或 Runtime 安装与清理；面板卸载不丢操作，窗口重建/归档/登出使过期操作失效                                                               |
| 失败降级       | 未支持、目标过期、回执未知、停止失败都保留内容并明确提示；禁止静默改成排队、停止跟踪或另开会话                                                                        |
| 权限与人工确认 | 不扩大工具权限，不更换账号和作用域；已有审批保持。按钮和快捷键引用同一命令及可用条件                                                                                  |
| 诊断           | 记录脱敏的操作类型、目标/消息标识、接收或拒绝原因、取消请求及终态时间；正文、附件和凭证不进入普通诊断日志                                                             |
| 验证           | 定向契约/竞态测试加真实 Electron + Runtime 用户动作，分别记录工程门禁和用户能力结果                                                                                   |

方案不需要违反[架构宪法](../architecture.md)。若实现发现必须新增第二个状态所有者、跨仓修改或改变 Runtime 生命周期边界，应先回到设计审查，不能借补充功能顺便重建整个 Agent 架构。

## 实现结果与交付审查

**结论：产品逻辑已明确，本地 Claude Code 最小闭环已实现；没有需要用户重新拍板才能开工的问题。** 效果图和设计已保存。工程检查与真实应用的通过范围分列在[验收记录](../testing/agent-follow-up-actions.md)，不能把本地通过扩大为所有 Runtime 通过。

| 拷问                                       | 当前结论                                                                                                                      |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| SDK 多消息是不是偷偷新开一轮 Studio 任务？ | 已验证补充保留同一 Run，得到匹配 UUID 的 started 回执及改变后的输出；不是暂停、终止后重发。模型是否采纳仍以实际执行结果为准。 |
| 发出取消请求是否足以开始 D？               | 不足。必须等目标 Run 确认取消；错误、超时、归档、工作空间变化均保留并暂停 D。自动化覆盖这些竞态。                             |
| 已开始的工具会被补充立即撤回吗？           | 不保证。需要结束原执行时使用停止；已完成写入和独立后台任务不承诺回滚或自动取消。                                              |
| 新草稿、附件、旧队列是否会混入补充？       | 纯文字补充固定旧上下文，新增图片/资源明确禁用；接收回执只更新对应历史消息。停止后执行保存自己的附件快照，旧队列继续暂停。     |
| 重启、未知回执会不会重复发送？             | 补充待接收状态恢复为未知，停止后执行意图恢复为普通暂停项；均不自动重发。不能承诺跨崩溃恰好一次。                              |
| 远程与 ACP 是否也已完成？                  | 没有。两项新增操作明确禁用；用户暂不登录 CCLink，不把远程夹具当真实远端执行。                                                 |
| 全部验收矩阵是否已完成？                   | 没有。本地核心动作已在真实 Runtime 验证；权限等待、原生中文输入法、多平台与真人现场验收仍有未覆盖项，详见验收记录。           |

本轮未更改工具授权、账号、收费或外部 Agent runtime。共用输入区使用统一命令与快捷键作用域；队列和草稿仍由原会话 store 管理，实际接收与取消由 Runtime/Bridge 管理。共享工作树内的模型用量和会话导航改动保持独立，本轮不提交或发布这些其他工作。
