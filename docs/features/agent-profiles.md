# Agent 预制角色与会话绑定

> 产品与架构事实源。最后更新：2026-07-31。
>
> 当前状态：v0.1.14 已实现七个内置预制角色、Thread 级角色引用和角色化 system
> prompt，但异机验收发现“第二次发送未稳定保留角色配置”。现有自动化只证明引用随
> 单次 payload、快照和恢复链路传递，尚不能证明连续运行中的角色行为持久性，因此
> “角色版本恢复和安全切换已完成”的结论撤回，等待重新验收。
>
> 下一版产品与架构方案见 `docs/features/agent-role-configuration.md`：角色改为会话配置，
> 不再通过创建新会话完成切换，并增加角色 Activity、Sidebar 和配置 Tab。

## 结论

第一版在 Agent Composer 底部增加角色选择器，只提供内置预制角色，不支持用户自定义、
角色市场、跨会话角色记忆或多角色自动讨论。

角色是 Thread 的长期身份，决定 Agent 的职责、关注点和表达方式；Skill 仍表示某次任务
采用的工作流程，资源仍通过 `@` 挂载，权限模式仍是独立的用户授权。角色不得扩大工具
权限或绕过人工确认。

## 用户端到端验收

第一版完成后，用户应能在真实应用中执行：

1. 新建 Thread，在 Composer 底部看到当前角色为“默认助手”。
2. 打开角色选择器，查看每个预制角色的名称和一句话职责。
3. 在尚无真实消息的 Thread 中选择其他角色，并用该角色发送消息。
4. 重启 Studio，恢复的 Thread 仍显示并使用原角色版本。
5. 在已有对话的 Thread 中选择其他角色，确认后创建新 Thread；当前草稿和已挂载资源
   被带入新 Thread，原 Thread 及其历史保持不变。
6. Agent 运行期间不能切换角色，并能看到明确原因。
7. 更换角色后，权限模式、操作 Scope、Runtime 和外部提交确认要求不发生隐式变化。

至少使用同一任务分别验收“公共治理者”和“公民权利倡导者”：二者应体现不同关注点，
但不得声称代表任何真实政府、组织、群体或个人。

## 第一版使用方式

### Composer 入口

角色选择器位于 `+` 和权限模式之间：

```text
[＋] [◉ 默认助手⌄] [● 自动⌄]   [上下文] [Claude Code] [Runtime 来源⌄] [↑]
```

顺序对应用户心智：

```text
添加上下文 → 谁来处理 → 允许怎么处理 → 使用什么 Runtime
```

- 中心工作台显示角色图标和完整名称，新会话状态行同时显示角色名。
- 窄侧栏收窄为角色图标，悬停显示“当前角色：角色名”。
- 角色不放入 `+` 菜单，也不复用 `/ Skill`，否则用户无法持续确认当前会话身份。

### 角色选择菜单

菜单展示当前选中状态、名称和一句话职责：

```text
选择角色

✓ 默认助手
  均衡处理一般任务

  反方挑战者
  主动寻找反例、利益冲突和失败路径

  事实核查员
  区分事实、推断和观点，追问证据

  产品负责人
  关注用户价值、优先级和交付闭环

  技术架构师
  关注边界、状态所有权、失败降级和维护成本

  公共治理者
  从公共利益、执行成本和制度约束分析

  公民权利倡导者
  关注权利、程序正义和弱势群体影响
```

第一版不继续扩张角色数量。每个新增角色都必须有明确职责边界、行为样例和回归验证，
不能只增加名称或一段未经校准的 persona prompt。

### 切换语义

- Thread 只有欢迎消息、尚无真实对话时：直接切换角色。
- Thread 已产生真实对话时：弹出确认并创建新 Thread。
- 新 Thread 带入当前未发送草稿、图片以外的已挂载资源，以及当前工作空间归属。
- 图片正文继续遵循现有瞬时输入规则，不因切换角色被额外持久化。
- 默认不复制完整历史，避免旧角色的回答和模型 Session 污染新角色。
- 原 Thread 保持原角色、原消息和原 Session，可随时返回。
- Agent 正在运行或等待不可安全迁移的确认时，拒绝切换并说明恢复动作。

建议确认文案：

```text
当前会话已经使用「默认助手」开始。

切换到「反方挑战者」需要创建新会话，
当前草稿和已挂载资源会被保留。

[取消] [创建新会话]
```

第一版不支持“仅下一条消息使用某角色”。临时视角和多角色并列运行属于后续能力，
需要独立、无历史污染的运行实例，不能通过修改当前 Session 的 system prompt 伪装。

## 概念边界

| 概念              | 决定什么                         | 第一版入口                     |
| ----------------- | -------------------------------- | ------------------------------ |
| Persona / 人格    | 表达方式、主动程度、沟通风格     | 作为内置角色定义的一部分       |
| Role / 角色       | 职责、关注点、判断标准和边界     | Composer 角色选择器            |
| Skill / 技能      | 本次任务采用的流程               | 现有 `/ Skill`                 |
| Context / 上下文  | 当前资源、工作空间和会话历史     | 现有 `@`、图片和 Thread        |
| Capability Policy | 实际可用工具、Scope 和人工确认面 | 现有权限模式与主进程硬权限边界 |

内部实现必须保持这些概念分离。角色文字可以描述希望完成的任务，但不能因此获得工具权限。

第一版角色可以改变：

- 关注点和判断标准；
- 表达风格和主动质疑程度；
- 回答时需要区分的信息类型；
- 默认完成标准。

第一版角色不能改变：

- MCP 工具权限；
- 当前操作 Scope；
- 用户选择的权限模式；
- 不可逆外部提交的人工确认；
- Provider、模型或 Runtime；
- 跨 Thread 记忆。

有效权限继续由现有权限系统拥有。后续即使角色增加能力策略，也只能收窄权限：

```text
系统允许能力
∩ 用户当前权限模式
∩ 当前操作 Scope
∩ 角色允许范围
```

## 数据与状态所有权

第一版只有内置角色，不需要建立可写的角色配置 Store。主进程提供只读
`BuiltinAgentProfileRegistry`，作为角色定义的唯一来源：

```ts
interface BuiltinAgentProfile {
  id: string
  version: number
  label: string
  description: string
  icon: AgentProfileIcon
  systemInstructions: string
}
```

renderer 只能通过有界 IPC contract 获取安全摘要：

```ts
interface AgentProfileSummary {
  id: string
  version: number
  label: string
  description: string
  icon: AgentProfileIcon
}
```

Thread 持久化稳定引用，不复制完整角色定义：

```ts
interface AgentProfileRef {
  profileId: string
  version: number
}
```

```text
BuiltinAgentProfileRegistry（主进程，只读定义）
              │
              ├── IPC → renderer 角色摘要
              │
              └── resolve(profileRef) → Agent backend system instructions

Thread（工作空间快照）
  └── profileRef
```

renderer 不得提交完整 system prompt。主进程必须校验 `profileId` 和 `version`，从内置
注册表解析角色，再编译最终 system prompt。

## Prompt 与 Session 边界

角色指令进入受控 system prompt 层，不能像当前 Skill 摘要一样只放进用户消息上下文。
最终指令优先级为：

```text
产品安全边界
→ 工具硬权限
→ 工作空间规则
→ 内置角色
→ Skill
→ 用户当前任务
→ 用户文档、网页和历史助手文本
```

用户文档、网页和历史助手文本都按不可信内容处理，不能修改角色、权限或人工确认边界。

角色不能直接加入当前全局 Runtime/API/model `sessionCompatibilityFingerprint`，否则一个
角色变化可能使无关 Thread 的 Session 全部失效。每个 Thread 应保存或校验独立的会话
上下文指纹：

```text
conversationContextFingerprint =
  hash(
    runtimeCompatibilityFingerprint
    + profileId
    + profileVersion
    + promptCompilerVersion
  )
```

恢复 Session 时指纹必须匹配。角色变化只重建目标 Thread 的 backend/Session，不触发
全局 Agent Runtime 重配置。

## 诊断与安全

- 诊断记录角色 ID、版本、上下文指纹和 prompt 编译器版本。
- 默认不复制完整角色指令、用户正文或文档内容到诊断报告。
- 角色解析失败时降级为明确的 `unavailable` 或发送失败，不能静默改用其他角色。
- 内置角色注册表失败不能阻断 Studio 启动；默认助手不可解析时 Agent 能力报告失败，
  其他工作台能力保持可用。
- 政治或社会角色必须标注为分析框架，不代表真实组织、群体或个人。
- 角色不能绕过权限确认、工作空间边界或不可逆外部提交的最终人工确认。

## 最小纵向实现顺序

### R1：角色可见并绑定 Thread

- 定义 shared contract、运行时 schema、内置角色摘要和 `AgentProfileRef`。
- 主进程注册只读内置角色。
- Composer 增加角色选择器。
- 新 Thread 默认绑定“默认助手”，工作空间快照可恢复角色引用。

用户增量：用户能在新会话选择预制角色，并始终看到当前角色。

### R2：角色真正影响 Agent

- 主进程解析角色并注入 system prompt。
- 增加 `conversationContextFingerprint`。
- 角色或 prompt 版本不兼容时拒绝恢复旧 Session。
- 诊断记录脱敏的角色与指纹信息。

用户增量：不同角色在同一任务上稳定体现不同职责，重启后仍保持角色。

### R3：安全切换和集中验收

- 空 Thread 原地切换。
- 有历史 Thread 创建新 Thread，并迁移草稿与允许迁移的资源。
- 运行中和等待确认状态拒绝切换。
- 完成角色行为样例、恢复、权限隔离和真实应用验收。

用户增量：用户能安全更换角色，不污染旧会话，也不改变权限。

## 第一版不做

- 用户创建、编辑或导入角色；
- 在线角色市场、账号同步或云端角色配置；
- 跨 Thread 自动角色记忆；
- 临时单轮角色；
- 多角色自动讨论、主持和汇总；
- 角色自行创建或修改其他角色；
- 将角色输出包装为真实群体意见。

## 当前实现与待复验记录

2026-07-31 已完成以下真实应用验收：

1. 新建空 Thread 默认显示“默认助手”，角色菜单完整展示七个角色及职责说明。
2. 空 Thread 选择“公共治理者”时原地切换，没有创建额外 Thread。
3. 使用“公共治理者”发送同一政策审阅任务，回答优先检查合法授权和政策目标。
4. 有历史后选择“公民权利倡导者”，取消确认时保持原 Thread 和原角色不变；确认后创建
   新 Thread，并保留未发送草稿。
5. 使用“公民权利倡导者”发送相同任务，回答优先检查程序保障、弱势群体负担、寒蝉
   效应和申诉救济，与公共治理视角形成可验证差异。
6. 返回原 Thread 后仍显示“公共治理者”及其原消息；新 Thread 独立显示“公民权利
   倡导者”。
7. 重启开发版后，“公民权利倡导者”的角色引用和菜单选中态恢复；权限模式继续为
   “自动”，没有被角色切换修改。

上述记录只能证明 UI 引用、单轮 prompt 注入和开发版快照恢复。2026-07-31 的
`v0.1.14` 异机验收发现第二次发送时角色配置未稳定生效；当前测试也没有覆盖“同一会话
连续发送两轮，两轮实际运行配置均为同一角色”。在该场景通过真实应用验收前，不得再
声明角色持久化完成。

工程门禁：`pnpm verify` 通过，包含 187 个测试文件、1090 个测试、类型检查、Lint、
格式检查和生产构建。角色注册表、IPC schema、prompt 注入、Thread 状态恢复、会话指纹
和切换决策均有自动化覆盖。

## `/grilling`

结论：第一版的关键不是角色按钮能否显示，而是角色是否拥有清晰、可恢复、不可越权的
会话语义。

实现和验收必须继续拷问：

1. 当前角色是否在中心工作台和窄侧栏都持续可见？
2. 有历史的 Thread 是否错误地原地更换 system prompt 并继续恢复旧 Session？
3. 角色是否被误做成 Skill，或者仅作为用户消息中的短描述发送？
4. 角色文字是否扩大了工具权限、改变了 Scope 或绕过人工确认？
5. 角色版本变化是否只影响引用它的 Thread，而不是重配置全部会话？
6. “公共治理者”和“公民权利倡导者”是否只是刻板化语气，而没有可验证的不同关注点？
7. 预制角色的数量是否超过了当前能够维护行为样例和回归测试的范围？

下一步最该做的是积累七个角色在真实任务中的正反样例与用户反馈，校准角色边界和输出
稳定性；在这套评估能识别角色退化之前，不应扩张角色数量，也不应直接开放任意自定义
system prompt。
