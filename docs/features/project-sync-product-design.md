# 项目同步产品设计

> 日期：2026-11-24。状态：评估与效果稿，**未实现**。用户 2026-11-24 确认：公司记录和公司账目也要跨电脑同步（取代此前“客户数据只留本机”的约束）；其余方向待确认。
> 效果稿：[项目同步](../design/project-sync-2026-11-24/README.md)。
> 参照：我的空间同步（[产品逻辑第 11 节](../design/personal-diary-space-2026-11-17/product-logic.md)、[GitHub 新建仓库](../design/github-new-repo-2026-11-24/mockup.html)、[验收](../testing/personal-diary.md)）。

## 结论

把“我的空间”已经验收过的自动双向同步推广到普通项目，**只对不是 Git 仓库的项目开放**（公司、文档、电子开发等）。用户在项目首页点“设置同步”，选“在 GitHub 新建私有仓库”或“使用已有仓库地址”，先看清“会同步 / 不会上传 / 只在这台电脑”，再点“保存并同步”。之后与我的空间相同：进入项目时、留在前台每个整点自动收发，状态栏显示“已同步 · 时间”；两边改了同一处就暂停，文字交给 AI 按用户的话合并，表格、Word、图片和 CAD 让用户选一份或两份都留。

**公司项目还同步公司记录（业务、客户与售后、经营决策）和公司账目（流水、确认与修改历史、原件）**。这些数据先加密再上传：第一次设置时用户设一个“同步密码”，另一台电脑下载后输入一次即可读出全部记录。同一条记录两边都改了，按记录逐条让用户选，不交给 AI；涉及金额和归属的流水绝不自动取舍。

本身已是 Git 仓库的代码项目不做自动同步，继续用左下角 Git 显式提交和推送。

## 现状评估

| 能力                                | 对象                  | 方式                                                                                                        | 现状                                               |
| ----------------------------------- | --------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 我的空间同步（`diary-sync`）        | 仅我的空间            | 自动双向；只同步日记、计划目录、项目设置和共享定时任务；分叉在临时 worktree 合并，冲突交给 AI，主分支只快进 | 真实 Electron 验收通过；GitHub 新建私有仓库刚上线  |
| 手动 Git 备份（`GitBackupService`） | 任意本地项目          | 一次性：提交全部可备份变更并 Push；单向；不拉取                                                             | 已实现，真人 GitHub 验收未做；目标演进是左下角 Git |
| 左下角 Git                          | 本身是 Git 仓库的项目 | 看变更、勾选提交、显式 Push                                                                                 | G1-G3 完成，Fetch / 远程关联未完成                 |
| 公司账目备份                        | 公司账目              | 导出数据库、原件和校验到文件夹，可在另一目录恢复                                                            | 已实现并验证恢复                                   |

问题：

1. **普通项目没有双向同步**。手动备份只上传不接收，第二台电脑改的东西回不来。
2. **同一项目可能出现三套入口**（手动备份、左下角 Git、我的空间式同步），用户分不清该用哪个。
3. **公司数据无法跨电脑**。`company.sqlite`、`accounts.sqlite` 与原件都在 `.cclink-studio/` 下，现有 Git 规则一律排除；而且 SQLite 是单个二进制文件，两台电脑都写时 Git 只能整份覆盖，必然丢记录。第二台电脑打开项目会看到空公司，“开始使用”后两份记录永远分叉。
4. **项目比日记大得多**。整目录上传会碰到视频、STEP 等大文件（GitHub 单文件上限 100 MB）、`.env`、依赖目录；必须有上传预览。

推广的可行性高：`syncDiary` 的核心（初始化、范围校验、敏感文件拦截、上传历史检查、临时 worktree 合并、冲突暂停与反馈、只快进、上传后核对）与“日记”无关，只有“同步哪些路径”是日记专有的。公司数据需要额外的一层：把数据库里的记录转成可合并、已加密的文件。

`project.json` 不同步，所以下载下来的副本获得新的稳定身份，符合“复制不继承绑定”的既有规则。

## 公司数据怎样同步

SQLite 继续是本机的工作数据库，所有读写仍只经过 `CompanyWorkspaceService` 和 `CompanyAccountsService`。同步时由这两个服务在项目里维护一份**同步副本**，Git 只同步这份副本：

```text
.cclink-studio/shared/company/
├── manifest.json                 格式版本、公司 ID、加密参数（盐、KDF 参数、密码校验值），无明文业务内容
├── records/<表>/<记录 ID>.enc    一条记录一个文件：完整当前内容 + 版本 + 修改历史，AES-256-GCM 加密
└── originals/<sha256>.enc        账目原件，按内容哈希，写入后不再改变
```

每轮同步：

1. **导出**：服务把上次导出后变更的记录写入副本（数据库为每张表记住已导出版本）。
2. **Git 同步**：与普通文件相同。不同记录是不同文件，两台电脑改不同记录不会冲突；只有同一条记录两边都改才冲突。
3. **冲突**：副本里的冲突不交给 AI。Studio 解密两个版本，按字段显示差异，用户逐条选择；选择结果写回副本，一并上传。
4. **导入**：服务在一个数据库事务里读入变更的记录；失败则整轮回滚，同步暂停，“公司记录无法读入”，本机数据保持原样。
5. 只有导入成功且两端一致后，才更新“已同步 · 时间”。

规则：

- **账目去重**：两台电脑各自导入同一份对账单时，流水的 `source_key` 相同、原件的哈希相同，导入时视为同一笔，不生成重复记录；两边对同一笔的确认或归属不同则进入记录冲突。
- **删除**：记录删除以删除副本文件表示；一边改、一边删时暂停询问。现有客户记录不能删除，业务项目只能归档，账目修改带历史，因此删除很少。
- **公司身份**：`manifest.json` 记录公司 ID。仓库里已有另一家公司的副本时拒绝合并，提示下载到新目录。
- **版本**：副本格式升级时旧版 Studio 暂停并提示“请先更新 Studio”，不降级写入。
- **加密**：密钥由同步密码经 scrypt 派生。同步密码保存在本机明文凭证文件（`CredentialService`，与 ADR 0003 一致，不用系统钥匙串）；文件名只用 UUID 和哈希，提交信息不含业务内容，诊断不含解密内容。更换密码会在原电脑重写全部副本，其他电脑需输入新密码。
- **只用私有仓库**：在 GitHub 新建时只建私有仓库，同名公开仓库拒绝；使用 GitHub 地址时每次上传公司副本前检查仓库仍为私有，变为公开即暂停；非 GitHub 地址无法检查，首次设置时明确提示。

## 自动时机与状态

与我的空间第 11 节完全一致，只把“进入我的空间”换成“进入这个项目”：进入（切到项目、启动恢复到项目、窗口回到前台）立即同步一次；留在前台每个整点一次；错过的整点不补跑；手动“立即同步”随时可用；同一项目同时只跑一轮。**只同步当前激活的项目**，后台项目只在本机检测“有待同步的改动”并显示小点，不在后台联网。

状态栏、首页标签和同步页共用四种状态：同步中… / 已同步 · 时间 / 有待同步的改动 / 同步暂停 · 查看原因。暂停原因：冲突待决、大量删除待确认、需要同步密码、公司记录无法读入、仓库变为公开、认证失效、范围外或敏感文件、网络失败。网络失败下次触发自动重试；其余等用户处理，进入和整点不会重复弹窗。

## 架构边界（实现前须满足）

- **状态所有者不变**：同步执行由 `GitWorkspaceService.transfer` 拥有，新增 `action: 'project-sync'`，与 `diary-sync` 共用同一引擎；把 `syncDiary` 的“同步路径”参数化，不复制第二个同步器。公司记录与账目仍分别只由 `CompanyWorkspaceService`、`CompanyAccountsService` 拥有；同步副本是它们导出导入的格式，不是第二份事实源，任何界面都不直接读副本。绑定地址与上次结果存在 `WorkspaceStateService` 的项目段 `project-sync`。
- **路径规则**：`cclink-studio-path-policy` 的允许列表增加 `.cclink-studio/shared/company/`，并校验其中只有加密文件和 `manifest.json`；明文 SQLite 仍禁止进入 Git。
- **一个项目只有一个入口**：设置了项目同步的项目，状态栏显示同步状态，不再显示手动备份；手动备份已绑定的项目提供一次“改为自动同步（沿用原仓库）”。左下角 Git 只服务原本就是 Git 仓库的项目。
- **准入**：文件夹不是 Git 仓库，或是由项目同步初始化的仓库；位于另一个仓库内、是我的空间、远程项目、只读目录时不提供。
- **权限与凭证**：沿用已保存 GitHub Token 的 `GIT_ASKPASS` 与本次 SSH 私钥路径；不读系统钥匙串。
- **人工确认点**：首次上传前的范围预览与同步密码；文字、记录和二进制冲突；大量删除；更换地址或密码；停止同步。自动同步本身不需要确认。
- **降级**：没有 Git、没有网络、未保存 GitHub 账号、未输入同步密码、同步失败时，本机项目文件、Agent、浏览器、终端、公司首页和账目全部照常可用，只是暂不和另一台电脑一致。
- **诊断**：同步页“最近几次”显示每轮收到/上传的文件数与记录数、失败原因；错误可复制且已脱敏。
- **ADR**：数据外发范围从“日记和共享设置”扩大到“整个项目 + 加密的公司记录与账目”，并改变此前客户数据只留本机的约束。实现前提交 ADR 0026。
- **界面文案**：客户与售后页目前写“记录只保存在本机……不上传”，在公司记录同步上线的同一版本改为如实说明“开启同步后加密上传到你的私有仓库”。

## 真人验收（实现后）

1. 在公司项目“蜗牛眼镜”首页点“设置同步”，选“在 GitHub 新建私有仓库”，设同步密码，核对范围后“保存并同步”。预期：GitHub 私有仓库里有项目文件和 `.cclink-studio/shared/company/` 下的加密文件；搜不到任何客户名、金额或明文 SQLite；没有大文件和 `.env`。
2. 在第二台电脑（或第二个用户目录）“从 GitHub 下载项目”，输入同步密码。预期：公司首页待办、收支、客户记录、业务与流水原件和第一台一致。
3. 在第二台修改一篇推广稿、新记一条售后、确认一条流水；回到第一台切进项目。预期：不点任何按钮，三项都已出现，收支同步变化。
4. 两台同时改同一段文字。预期：暂停；输入处理意见后两边一致。
5. 两台同时改同一条售后记录的状态，以及同一笔流水的业务归属。预期：按记录逐条让你选，选完两边一致，月度汇总正确。
6. 两台各自导入同一份对账单。预期：没有重复流水。
7. 两台同时改同一份表格；第二台删掉一个含 30 个文件的目录。预期：表格可选一份或两份都留；删除先暂停询问。
8. 断网、清除 GitHub Token、输错同步密码、卸载 Git 各试一次。预期：本机功能可用，状态如实。
9. 打开 cclink-studio 代码项目。预期：显示“由 Git 管理”，没有自动提交。

## 实现顺序（每步都有用户可验收结果）

1. **项目文件双向同步**：首页卡片、设置页（复用 `DiarySyncChoice`）、范围预览、`project-sync` 动作、自动时机、大量删除保护、二进制“两份都留”。验收 1（不含公司数据）、3、4、7、8、9。
2. **第二台电脑**：从 GitHub 下载项目（列出私有仓库）。验收 2（不含公司数据）。
3. **公司记录**：同步密码、加密副本、导出导入、记录冲突画面、第二台解锁。验收 1、2、3、5 中的客户与业务部分。
4. **公司账目**：流水、修改历史、原件、跨电脑去重。验收 3、5、6 中的账目部分。
5. **合并入口**：手动备份项目迁移为自动同步，移除重复入口。

## 需要你决定

1. **同步密码是否必须**。推荐必须：公司记录含客户联系方式和对账单原件，仓库即使私有也在第三方平台上；加密后即使仓库误设公开、账号泄露也读不出内容。代价是第二台电脑要输一次密码，忘记密码时只能回原电脑处理。
2. **单文件上限 50 MB 是否合适**。超过的视频、STEP 文件首版不同步。
3. **代码项目是否完全不碰**。推荐是；否则自动提交会污染代码历史、绕过分支和 CI。

## /grilling

- 最危险的失败不是同步失败，而是**把不该外发的东西传上去**：整个项目范围远大于日记，首次预览、敏感文件拦截、上传历史检查和“副本目录只允许加密文件”是首版门槛。预览统计必须来自真实将要提交的文件列表。
- **公司记录的最大风险是静默丢失或重复**：导入必须整轮事务化；账目必须靠 `source_key` 与原件哈希去重；同一笔流水两边确认不同必须停下来，否则月度汇总会悄悄出错。验收要用真实月份复核汇总前后一致。
- **同步副本可能与数据库不一致**（导出中途退出、手工改了副本）。每轮导出前要按版本对账，副本校验失败只暂停，不能用副本覆盖数据库。
- **删除是双向的**。大量删除保护和“没选的那份可找回”必须在第一版就有。
- **二进制冲突比文字冲突常见**（报价单、Word、设计稿），首版至少要有“两份都留”，不能卡死在暂停。
- **密码丢失**：只有原电脑还能读数据；更换密码要重写全部副本，期间其他电脑暂停。要在设置时说清楚。
- 同步依赖 GitHub 可用和 Token 有效；Token 过期时自动同步会持续暂停，状态栏必须一直可见。
- 这份设计只有效果稿，没有任何实现；效果稿检查只说明页面可演示，不代表能力存在。
