# 公司工作空间实现方案

> 状态：首个纵向闭环已实现并通过自动化门禁；普通工作验收、发布关联与决策批次尚未实现，真实 App 真人验收待完成；产品范围已由用户确认。
> 日期：2026-10-14。
> 产品事实源：[公司工作空间产品设计](company-workspace-product-design.md)。
> 首版布局：经营导航。经营收件箱仅保留为设计对比，不进入首版实施。

## 实现结论

在现有 Studio 内新增一个公司领域模块，拥有业务项目、普通工作的计划和验收、资料关联及经营决策。公司界面读取既有财务、Agent、网页事务和发布事实，使用原执行入口推进工作。

首版保持本地、单人、免登录。公司是工作空间的经营视图配置，不新增 `WorkspaceRef.kind`、公司登录体系、独立 App 或工作空间恢复流程。财务、项目管理和运营均纳入首版，按可验收的用户动作分批接入。

正式实现先交付“启用公司视图 → 创建业务项目 → 关联真实资料与已有账目 → 下钻原记录”。随后在同一项目上接入受控 AI 产物及验收，再关联单篇发布结果。工程准备只做到当前闭环需要的范围。

## 本地数据与最小对象

选择独立的工作空间内 SQLite，使用现有 Electron Node 的 `node:sqlite`，不新增原生依赖。公司与账目分库，按唯一 owner 分离写入；原账目路径、数据库与记录不迁移。

选择 SQLite 是因为项目、资料引用、工作计划与验收需要同一事务提交和版本冲突检查；散落 JSON 文件会把一致性、唯一绑定和恢复逻辑转移到手工写入协议。复用当前财务模块已有的技术路径，但公司数据库只存自己的业务事实，不能成为全模块状态库。

```text
<workspace>/.cclink-studio/
  company-workspace/company.sqlite
  company-accounts/accounts.sqlite       # 既有财务数据
  company-accounts/documents/            # 既有原件
<workspace>/<用户选择的产物目录>/
  产品介绍稿.md
  经营回顾.md
```

| 对象     | 保存内容                                               | 明确不保存                          |
| -------- | ------------------------------------------------------ | ----------------------------------- |
| 公司配置 | 视图启用、显示名称、schema 版本                        | 新工作空间身份、登录或法律主体认证  |
| 业务项目 | 稳定 ID、名称、目标、交付条件、可选日期、归档标记      | 独立 Browser、Terminal 或会话状态   |
| 资料关联 | 业务 ID、带类型的原对象引用与来源版本                  | 全量聊天、凭证正文、Cookie、Token   |
| 普通工作 | 目标、被接受的计划版本、输入引用、输出位置、原运行引用 | 独立运行状态、每一步 operation 账本 |
| 验收记录 | 实际产物路径、内容摘要值、用户决定、版本、时间         | AI 自述成功、平台发布终态           |
| 运营内容 | 业务 ID、原稿引用、准备工作 ID、发布事务 ID            | 账号登录态、发布步骤副本            |
| 决策记录 | 用户确认的决定、来源引用、适用业务、取代关系           | AI 摘要直接变成公司决定             |

数据库表随批次增加：第一批仅配置、业务项目、资料关联；第二批增加普通工作和验收；第三批增加确有需要的运营内容关联；最后增加决策。没有空员工、预算、库存、调度或通用事件表。

所有领域写入通过主进程队列和 SQLite 事务提交。修改携带对象预期版本，冲突返回结构化错误并重新读取，避免旧表单覆盖新决定；不能建立额外通用事务框架。用户界面在写入成功后才更新成功状态。

工作空间身份从现有 WorkspaceStateService 取得，数据库只引用该身份，不生成第二份 workspaceId。路径规范化、目录移动及复制继续遵守基础层已有身份规则。

数据库损坏或版本不支持时进入可诊断的只读故障态，不用空库覆盖。Schema 升级采用本模块有界事务和升级前备份，失败时保留原库。公司资料备份在本服务写队列内取得元数据快照，并校验选定产物的版本；账目调用原备份能力，分别记录来源和取得时间，不宣称多个数据库共同原子备份。恢复说明列出公司元数据、实际产物和原领域资料的覆盖范围；凭证与发布结果不靠复制引用假装备份完整。首版不自动同步或提交经营资料到 Git。

## IPC 与权限边界

公司请求携带 `workspaceRef` 和具体业务对象 ID。主进程校验可信主工作台 sender、已授权本地目录、基础层 workspaceId 和对象归属；拒绝 global、remote、跨工作空间对象、路径越界及失效授权。

首批 API 只覆盖查询快照、启用视图、创建／修改／归档业务项目、关联／解除关联。后续按纵向闭环增加工作计划接受、产物检查、验收、内容关联和决策确认。禁止暴露 `writeSnapshot`、任意 SQL、任意完成状态、任意账目确认或代替发布守卫的通用命令。

每个 IPC 通道、参数 schema、错误和释放逻辑来自同一 shared contract。错误至少区分不可用、工作空间失效、版本冲突、资料缺失或变化、运行关联失效、保存失败和原领域失败；不给 UI 一个无法判断归属的字符串。

公司变更事件只包含 workspaceId、领域 revision、对象 ID 和类别，不携带业务正文。Renderer 收到事件后重新查询主进程事实；订阅随工作空间切换释放，过期 generation 的响应不得投影到新工作空间。

新操作使用现有稳定 command 和 contribution 入口：启用公司、打开公司、创建业务项目、打开工作、验收产物。工具栏和上下文入口共享命令；不新建独立右键菜单或权限系统。

## AI 普通工作的执行与验收

第一条受控 AI 工作选择“根据选定的产品规格与试戴记录，保存一篇 Markdown 稿件”。它只需要资料读取和指定产物写入，不以整个公司、全部账号或工作空间目录可见作为授权。

1. 用户接受目标、资料列表、输出位置和完成条件，公司服务固定计划版本。
2. 复用原会话创建与 `createConversationRunController`。主进程从任务引用解析可信工作范围；renderer 不传入一份可以自行扩大权限的 allowlist。
3. 为既有 Agent 消息 contract 增加可选、类型化的公司工作引用，缺失时原普通会话行为保持原契约。绑定验证和工具范围由主进程编译，再交给原 AgentBridge。
4. 公司保存 conversationId、runId 及接受的计划版本引用；运行开始、终态和取消由原 AgentRuntimeStateStore 拥有。相同工作启动串行校验，避免双击产生两轮工作；启动响应未知时先查询原运行，不能立即重发。
5. 使用既有授权 broker、MCP session context 和本地 Claude Code SDK 的工具限制入口。公司准备工作只允许选定资料读取、指定 Markdown 输出及必要的公司候选建议工具；拒绝读取凭证／内部控制数据、任意 Bash、外部 MCP 和对外副作用。路径校验通过真实路径和最近存在父目录处理符号链接与尚未创建的输出文件，不能只比较路径前缀。
6. 原运行终态只证明这轮执行结束。公司服务检查约定产物真实存在、非空、大小有界，并取得该版本摘要值；产物合格后投影为“待验收”。运行失败或没有产物时保留实际失败、已有材料和允许下一步。
7. 用户打开产物后点击验收。主进程重读同一文件版本，再保存验收决定；内容变化时拒绝旧版本确认并重新检查。AI 没有用户验收命令。
8. 切换页面、工作空间或重启后，通过保存的运行引用重新查询。原 owner 报失去 Runtime 时显示中断；原记录被淘汰则显示不可查询。两者均不自动重跑；已保存的真实产物与用户验收可以继续查看。

公司模块如需要模型写入建议，只增加“读取当前公司上下文”和“提出工作／决策候选”的有界工具。它们只能作用于主进程绑定的业务及当前工作，不能接受模型自报身份或调用完成、财务确认与发布授权。发布流程仍使用原长 Agent Run 与 Runtime handshake，不增加公司 claim/report MCP 或短 Run 调度。

首版以默认本机 Claude Code SDK 运行上述受控准备闭环。其他 Runtime 只有在同等工具边界被实际验证后才开放公司受控工作；普通 Studio Agent 的现有能力不因公司模块受限而被关闭。工具可见列表与提示词不能替代 broker 的真实拒绝检查；第二批必须验证原生工具和 MCP 两条入口都无法绕过。

## 财务和运营接入

财务只读取 CompanyAccountsService 的原确认记录和原汇总。增加内部有界的工作空间查询方法，供公司主进程聚合使用；旧入口继续转发到同一读取逻辑。UI 修改及确认仍走原财务 contract，成功后发带工作空间归属的失效通知，让公司快照刷新。

账目归属由用户显式绑定。主进程验证归属存在且属于当前工作空间，并约束一个财务归属最多关联一个业务项目；更换绑定只影响关联，不改历史流水。公司总额读取原月份汇总，不能把各项目汇总相加再当公司总额。

运营创建或关联原 ArticlePublishingService / WebAffair 对象后，保存返回的稳定 affairId。原稿、实际账号、正文与逐图步骤、保存与提交授权全部在原发布入口配置和执行，公司不复制发布表单或状态机。

创建外部事务与保存公司关联不能假装是一个跨数据库原子事务。先固定公司内容项 ID，再调用原创建入口，成功后保存返回引用；重试前查询已有明确关联。结果不确定时提供“选择已有发布任务”恢复，不凭相同标题猜对象或再次创建并启动发布。不为此新增 operation 账本。

公司运营页显示原状态和证据，点击继续、终止或只读核验仍调用原受校验动作。任何当前守卫要求的人工接管都如实保留。真实发布授权必须包含具体账号、文章和影响范围；本产品设计确认不等于未来真实文章的公开发布授权。

## 生命周期与恢复

公司模块通过现有 ServiceRegistry 的一份 start/stop 声明接入。启动尝试内部处理可选模块失败，向界面提供 `ready/degraded/unavailable/failed`，不把公司初始化异常抛成整个 Studio 启动失败。

IPC 使用本模块受信任注册 scope，停止时只释放自己的 handler；MCP contribution 进入原工具宿主，随宿主停止释放。所有订阅、文件检查和短期启动互斥均有同一 owner 的释放路径，窗口重建与重复启停保持幂等。

用户启用公司时才初始化该目录的公司数据；应用启动不遍历全部公司目录。切换时旧任务继续固定归属，界面解除旧订阅，并用原 Workspace transition generation 防止旧快照覆盖新页面。

工作恢复不读取 renderer 的“运行中”来判断 Runtime，也不靠计时、页面是否打开或 Agent 自述猜成功。财务与发布服务不可用时，公司其他页面继续可用，相关摘要显示不可用与最后核验时间。

## 按用户动作分批实施

### 第一批 公司入口与真实业务关联

用户可以打开普通本地目录、启用公司视图、创建 AR 眼镜业务项目，关联真实文件、当前工作空间已有会话和既有账目归属。项目支出能打开原记录；公司重启后仍能打开相同项目和资料。

本批只新增最小公司存储与 contract、经营导航和项目／资料页。总览查询既有数据并明确未启用或不可用的领域；财务操作进入原工作台。运营可关联已有原稿及发布事务，并打开原发布页，不创建假内容或假状态。

验收包括公司零配置启用、A/B 工作空间切换、相同财务归属重复绑定拒绝、引用失效、只读目录与损坏库降级、关闭公司视图后本地功能仍可用。该批成功只声明“公司业务组织与原记录下钻”完成。

### 第二批 AI 准备真实产物与用户验收

用户从项目工作中固定资料与输出范围，启动真实 Agent，打开实际保存的 Markdown 产物并验收。材料缺失、产物变化、启动失败与中断有明确状态及可执行下一步；重启后能查询原工作并继续。

改动只包括公司工作绑定、现有授权入口的范围收窄、真实产物检查和验收记录。第一个 smoke 必须同时证明真实文件输出和拒绝越界；不能只交付提示词、计划清单或模拟状态。

### 第三批 财务与单篇运营结果回到业务项目

用户用一个真实月份完成导入、AI 建议、人工确认、汇总、导出与备份恢复；确认后公司页直接显示原服务的新结果。用户把第二批稿件绑定一条真实发布事务，检查具体平台与账号，完成实际提交及公开结果核验。

核验矩阵分别覆盖细步骤观测、公开提交、平台拒绝、等待审核、未知提交与只读恢复。未取得真实发布授权时继续完成配置和保存等已授权工作，公开提交验收保持待办；不把保存草稿冒充完成。

### 第四批 经营回顾与首版整体验收

用户从已关联会话确认一条经营决策，查看其来源；让 AI 基于已确认支出、验收产物和平台回执准备一份带出处的经营回顾。定时触发仅通过用户显式配置的原定时任务，本轮不默认启用提醒。

用户完成产品文档完整端到端验收，覆盖关闭重启、资料变化、退回验收、原服务故障与公司模块停用。三个领域均取得真实业务结果后，才能声明首版公司经营闭环完成；第四批也不以测试数或代码量代替该判断。

## 工程准备度和验证

当前用户功能进度：公司入口、公司业务关联及普通工作验收尚未实现。当前工程准备度：产品范围与实现方案已落盘，效果稿交互检查通过；功能代码、源码门禁和真实公司闭环均未验证。

每批补当前改动必要的 domain、contract、授权和恢复测试，随后运行受影响 smoke。阶段合入遵守架构宪法的源码门禁；首版完整交付前执行 `pnpm verify` 与真实 App 验收。效果稿测试不计入功能验证。

| 必测边界          | 核验事实                                                          |
| ----------------- | ----------------------------------------------------------------- |
| Sender 与目录授权 | 网页、辅助窗口、任意路径、remote/global 和跨业务对象均被拒绝      |
| 并发与持久化      | 旧版本修改不覆盖；写失败不显示成功；归档与恢复保留关联            |
| 工作绑定          | 双击只有一轮；未获真实启动不显示执行中；旧运行结果只回到原归属    |
| 工具授权          | 公司准备工作不能用原生工具或 MCP 改账、改验收、写控制库或对外提交 |
| 真实产物          | 空文件、错误路径、符号链接越界、执行失败、验收前变化均拒绝伪成功  |
| 财务事实          | 待核对不计入，确认后刷新；账目未齐不显示完整利润，关联不双计      |
| 发布事实          | 草稿与公开结果区分，未知提交不重发，账号与正文／逐图证据可核对    |
| 生命周期          | 重启显示原 owner 的中断事实；切换解绑订阅；重复重建不累积 handler |
| 降级              | 无登录、远程离线、公司／账目／Agent 故障均不阻断其余本地能力      |

公司视图影响导航和 Workbench 可用宽度。如果实施实际改变了 Browser 原生 View 的可见性、bounds 或缩放链路，必须重跑项目规定的真实 Electron 缩放／遮挡验收；仅新增普通公司页面时，不借机调 Browser 阈值或重构布局 owner。

## 拷问与止损

结论：最大实现风险在跨领域归属、可信运行绑定和验收证据，工程量应围绕这三件事收敛。整体 UI 不能先铺满再等待真实链路补齐。

- 公司总览是否减少找资料和重新交代背景？第一批就用真实业务下钻验证；不先增加无来源的经营指标。
- AI 是否有稳定运行事实与真实文件？第二批同时验收输出与拒绝越界，`succeeded` 不自动等于用户验收。
- 财务／发布是否出现第二份状态？公司表中禁止保存原领域状态和步骤成功副本，失效后重新查询原 owner。
- 备份是否只复制了引用？恢复验收明确检查公司数据、实际产物及账目原件，原服务备份范围需可见。
- 一个前置问题是否正在替代主线？单项超过 60 分钟或同一阻塞连续失败两次，停止扩张，说明已得到的用户能力、替代路径和下一步取舍。

实施入口是第一批的最小真实闭环。多人权限、预算报销、运营 ROI、员工中心、通用任务平台、数据库框架及云端部署均不作为隐藏前置条件。
