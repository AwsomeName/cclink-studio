# ADR 0003：开源版使用本地明文凭证存储

- 状态：accepted，implemented
- 日期：2026-07-28
- 负责人：CCLink Studio Maintainers
- 取代范围：`docs/architecture.md` 中“凭证必须使用本机加密存储”的要求，以及 ADR 0002 中关于 `safeStorage` 的凭证存储决定

## 结论

CCLink Studio OSS 不依赖 CCLink 账号、CCLink 云服务或操作系统钥匙串。用户主动配置的第三方凭证由 Studio 持久化到 Electron `userData` 下的独立明文文件。

凭证可以被用户显式显示、复制、替换和清除。它们不得进入工作空间、普通设置、日志、诊断报告、崩溃信息、Git 备份或 renderer 全量状态。

本决策已经实施。生产代码统一使用 `CredentialService` 和本地明文凭证文件，`verify:credential-boundary` 阻止重新引入 `safeStorage`、keytar 或 Keychain 调用。安装包与真人验收状态见 `docs/features/local-credentials-development-plan.md`。

## 问题

旧实现使用 Electron `safeStorage` 保存 Agent、Meshy、GitHub 和数据源凭证。在 macOS 上，`safeStorage` 依赖 Apple Keychain。这个实现解决了旧版凭证明文混入普通设置的问题，但产生了新的产品和架构问题：

1. OSS 本地工作台在没有 CCLink 登录需求时仍会触达系统钥匙串。
2. 三个领域分别实现凭证文件，形成重复的存储、错误和迁移逻辑。
3. “系统加密存储不可用”会阻止用户保存第三方凭证，旧版迁移失败时还可能阻塞普通设置写入。
4. 文档对“Studio 是否保存模型 API Key”存在互相冲突的描述。
5. 现有安全表述没有区分“防止意外泄漏”和“抵抗已经取得当前用户权限的恶意程序”。

## 决策

### 1. 产品边界

- OSS 默认不提供 CCLink 登录，不连接 CCLink 云服务，不初始化或调用系统钥匙串。
- Studio 可以保存用户主动提供的第三方凭证，包括模型 API Key、GitHub Token、数据源认证信息和已启用扩展的服务密钥。
- 凭证只保存在当前设备，不自动同步，不跟随项目复制，不进入 Git 备份。
- 用户拥有凭证，可以在明确操作后显示、复制、替换或删除。

### 2. 唯一状态所有者

新增主进程 `CredentialService`，作为所有 Studio 管理凭证的唯一状态所有者。

`CredentialService` 负责：

- 加载、校验和原子写入凭证文件；
- 串行化并发修改；
- 检测运行期间的外部文件修改并阻止覆盖；
- 提供脱敏元数据；
- 处理定向显示、复制、替换和清除；
- 为 Agent、Git、数据源和扩展解析凭证；
- 报告 `ready`、`degraded`、`conflict`、`unavailable` 和 `failed` 状态；
- 生成不包含凭证值的诊断信息。

Agent、Git 和数据源不得继续拥有独立的凭证文件或第二份内存状态。

### 3. 持久化

默认路径：

```text
{userData}/credentials/credentials.json
```

文件使用带版本的 JSON schema，macOS/Linux 权限为 `0600`。写入必须采用串行队列、同目录临时文件和原子替换。Store 必须保存已加载文件的版本摘要，写入前发现磁盘文件被外部修改时进入冲突状态并要求重新加载，不得覆盖外部修改。解析失败时保留原文件并进入 `degraded`，不得把损坏文件静默当作空凭证后覆盖。

普通设置和工作空间配置只保存非敏感配置及稳定 `credentialRef`。

### 4. Renderer 与 IPC

- Renderer 默认只能读取凭证 ID、类型、是否配置、更新时间和使用者等元数据。
- `revealCredentialField(id, field)` 是用户明确触发的定向读取，不提供“读取全部凭证”接口。
- `copyCredentialField(id, field)` 由主进程直接写系统剪贴板，避免凭证进入 Zustand、React 状态或诊断快照。
- 写入、显示、复制和删除都必须经过 trusted renderer guard、严格 schema、长度限制和稳定错误码。
- Agent 和其他自动化能力不得调用 reveal/copy，只能由领域服务在主进程内部解析已授权的凭证。

### 5. 安全声明

本方案保护：

- 凭证不被误写入项目、Git、普通设置、日志和诊断；
- 凭证写入过程不因中断产生半文件；
- 普通跨用户文件访问受到操作系统文件权限限制；
- Renderer 常规状态和不可信内容无法批量读取凭证。

本方案不保护：

- 已取得当前系统用户权限的恶意程序；
- 管理员、整机控制者或未加密磁盘备份；
- 用户主动复制或上传凭证文件。

产品和文档必须称其为“本地明文凭证”，不能称为“安全加密存储”。

### 6. 旧凭证

新默认路径不得导入 `safeStorage`，也不得在启动时尝试解密旧文件。

检测到旧 `secrets.enc` 时，只报告存在旧版凭证并引导用户重新输入。新凭证写入并验证成功后，用户可以删除旧文件。为了保持“无钥匙串依赖”，OSS 应用内不提供旧密文自动导入。

## 不变量

- 无凭证、凭证文件缺失或凭证服务失败都不得阻断应用启动。
- 凭证值不得进入工作空间、普通设置、日志、诊断、遥测、MCP 返回、Agent 消息或 Git 提交。
- 不得把凭证和工作空间状态放进同一个持久化事务。
- 不得在 renderer 提供批量列出明文凭证的能力。
- 不得通过固定密钥、机器标识或与密文同目录的自动解密密钥伪装“加密”。
- OSS 默认生产路径不得 import `safeStorage`、`keytar` 或 Apple Keychain API。

## 备选方案

### 继续使用 `safeStorage`

优点是静态磁盘泄漏时保护更强。拒绝原因是 macOS 上依赖 Keychain，与 OSS 无系统钥匙串依赖的产品边界冲突。

### 主密码加密库

安全边界更强，但每次启动需要解锁，忘记密码无法恢复，当前产品没有提出该复杂度需求。后续如引入，必须作为新的显式存储模式和独立 ADR，不能静默改变现有文件。

### 本机密钥文件加密

自动解密密钥与密文都可被当前用户读取，只能提供混淆，不能形成可信的额外安全边界，因此不采用。

### 只读取环境变量

适合高级用户，但不能满足普通用户长期配置、显示、复制和管理第三方凭证的需求。环境变量可作为补充来源，不作为唯一方案。

## 风险与影响

- 用户目录或整机备份泄漏时，第三方凭证可能直接暴露。
- 明文文件必须被所有诊断、导出、Git 备份和文件搜索能力排除。
- 显示和复制功能扩大了定向 IPC 权限面，必须保持显式用户动作和最小返回范围。
- 凭证文件损坏不能静默清空，否则后续保存会造成不可逆数据丢失。
- 旧版密文不能自动迁移，用户需要重新输入凭证。

这些风险通过明确威胁模型、文件权限、存储隔离、原子写入、诊断脱敏和人工操作边界管理，不通过“本地加密”措辞掩盖。

## 迁移计划

迁移按 `docs/features/local-credentials-development-plan.md` 执行：

1. 固定共享 contract、凭证 ID 和持久化 schema。
2. 建立 `CredentialService` 和 `PlaintextCredentialStore`。
3. 建立设置页凭证中心及定向显示、复制、替换和清除。
4. 迁移 Agent/Meshy、Git 备份和数据源消费者。
5. 增加旧密文检测与重新输入提示。
6. 删除全部 `safeStorage` 生产导入和旧凭证 Store。
7. 完成自动化、smoke、打包应用和真人验收。

## 回收或复审条件

出现以下任一条件时必须重新提交 ADR：

- 产品要求抵抗当前用户权限下的恶意程序或未加密磁盘备份；
- 引入主密码、硬件密钥、系统钥匙串或企业密钥管理；
- 凭证需要跨设备同步；
- 官方集成需要托管官方账号或消息凭证；
- 第三方凭证需要进入团队共享或远程执行环境。

## 验证

- `rg "safeStorage|keytar|Keychain|keychain" src package.json pnpm-lock.yaml` 不命中生产依赖或生产代码。
- 无凭证、文件缺失、权限拒绝、JSON 损坏和写入失败时，应用与无关能力仍可启动。
- 凭证写入、重启恢复、定向显示、主进程复制、替换和清除均有测试。
- 凭证文件位于 `userData`，不位于工作空间，macOS/Linux 权限为 `0600`。
- 诊断、日志、MCP、Agent 消息、工作空间快照和 Git 备份不包含测试凭证。
- `pnpm verify`、受影响 smoke 和打包应用真人验收全部通过。
