# CCLink Studio 项目备忘录

> 本文件记录尚未进入正式方案的候选想法，以及已退出当前主线的暂缓事项；不是当前实现事实源。
> 最后更新：2026-08-25。

## cclink-agent 与 Studio 的本地 Runtime 统一：冻结

状态：2026-08-25 明确冻结，不继续实现、不切换默认后端，也不删除 Studio 现有 Runtime。

### 当前结论

- 取消“让 `cclink-agent` 成为 Studio 唯一本地模型/Runtime 执行后端”的当前目标。
- Studio 继续拥有本地 Thread、消息、run、Session、模型/Runtime 执行、工具、权限确认、
  Browser、Editor、Terminal、角色、Skills、定时任务和诊断。
- 若未来恢复 Studio 本地任务同步，`cclink-agent` 在该场景只作为消息转发候选：负责接收手机或
  远程消息、转发给在线的 Studio，再把 Studio 的流式回复和结果转回去；不拥有 Studio 产品状态，
  不决定权限，也不控制模型生命周期。没有运行 Studio 的远程电脑上，正常 Agent Runtime 职责
  不受影响。
- 停止等控制消息可以经过 `cclink-agent` 转发，但真正的判断、执行和终态仍由 Studio 拥有。
- 手机能力只在 Studio 在线时可用。Studio 关闭或离线时明确不可执行，不要求
  `cclink-agent` 独立运行模型或维持另一套本地 Agent。
- 现有实验性 `cclink-agent` HTTP/SSE backend、相关 ADR 和代码本轮不删除、不扩展；它们不再
  构成当前产品主线，也不得据此切换默认后端。

### 以后恢复讨论前先确认

1. 用户是否仍接受“Studio 不在线，手机能力不可用”。
2. `cclink-agent` 是否仍只做传输，不重新拥有 run、Session、工具、权限或 Runtime 状态。
3. 手机消息如何准确绑定在线 Studio、Thread 和 run，断线时如何明确返回不可用，而不是排队或
   静默改由 Agent 执行。
4. 只有边界和真人验收动作重新确认后，才决定保留、收缩或删除现有实验 backend；不得直接沿用
   “统一 Runtime”旧目标继续开发。

## 项目预览：本地 Web 服务管理

状态：候选想法，暂缓且不进入当前开发主线；不把端口列表或通用进程管理器当作产品目标。

### 产品结论

- 用户侧功能名称暂定为“项目预览”，底层候选能力为工作空间级的本地预览服务。
- 目标闭环是：用户在当前本地工作空间点击“启动预览”，确认待执行命令后，Studio 启动网页
  服务、识别真实本地 URL、在内嵌浏览器打开，并提供运行状态、日志、重启和停止入口。
- 单个静态 HTML 继续使用现有 `file://` 预览；只有模块加载、路由、构建工具或接口请求确实
  需要 HTTP 服务时才启动本地服务。
- 当前 HTML Browser 预览、Terminal 进程生命周期和 CLI 打开 URL 接管只是可复用基础，尚未
  形成服务端口、就绪状态、工作空间归属与停止/重启的一体化用户闭环。

### 暂缓决定与能力边界

- 当前没有足够高优先级的真实需求，不实施、不排期，也不作为发布门禁；以后想起或出现明确
  用户场景时再重新评审。
- 首轮若恢复，只做网页预览，不扩张为 Docker、数据库、任意守护进程或跨机器服务管理平台。
- Browser 只展示页面，关闭 Browser Tab 不应隐式停止服务；Terminal 继续拥有 PTY、进程和
  输出事实；候选预览服务只拥有预览定义、服务与 Terminal session 的关联、URL、端口、就绪
  状态和用户期望生命周期，不能复制 Workspace、Tab 或 Terminal 状态。
- 服务必须绑定明确的本地 `WorkspaceRef`。切换工作空间不能串服务；退出 Studio 时只能停止
  Studio 自己启动的进程；外部已存在服务最多标记为“已发现”，不得擅自终止。
- 默认只面向 loopback。检测到 `0.0.0.0` 或局域网暴露时必须警告；端口冲突时不得杀死未知
  进程，只能让用户换端口、查看占用或取消。
- 启动项目命令属于执行本地代码，必须由用户明确触发并看到命令；App 重启后默认不得静默
  自动运行，未来若增加自动启动也必须单独由用户启用。
- 缺少预览配置、命令失败、端口冲突或 Browser 不可用时，只降级项目预览，不得影响文件、
  编辑器、Agent、Terminal、数据源、Android 或 Studio 启动。

### 以后恢复时先验证

1. 先确认一个真实项目确实需要 HTTP 预览，且 `file://` 不能满足，而不是为了展示端口做功能。
2. 用户从工作空间内选择或确认 `dev`、`start`、`preview` 等候选命令，一次操作即可看到真实
   页面；Studio 展示实际 URL 和就绪/失败状态，不能只凭进程存在宣称服务可用。
3. 用户可以查看日志、重新打开页面、重启和停止；Browser Tab 关闭、工作空间切换和服务退出
   后状态仍然准确，不出现假在线或跨工作空间串联。
4. 故意制造端口冲突、命令立即退出、HTTP 长时间未就绪、局域网绑定和 Studio 重启，验证
   失败可诊断、未知进程不被终止、无关本地能力继续可用。
5. 只有上述真实应用闭环证明有持续价值后，才评审多服务、保存配置、自动恢复或更通用的
   “工作空间服务”模型。

## macOS 原生应用菜单补强

状态：低优先级，暂不进入当前开发主线；不把菜单栏扩展成第二个命令面板。

### 评估结论

- 截图顶部黑色区域是 macOS 原生应用菜单。当前没有必要为它增加复杂的 Studio 业务入口，
  现有工具栏、快捷键、命令面板和上下文菜单已经覆盖主要操作。
- 若以后补强，只考虑“打开工作空间”“保存”“设置”三个高频入口；撤销、复制、粘贴等
  编辑动作继续使用系统原生角色。Agent、远程、数据源等复杂操作不进入首轮菜单。
- 截图中的白色窗口标题区域不承担新的业务功能。若它与当前 `hiddenInset` 和应用顶栏设计
  不一致，应先排查运行版本或窗口样式，而不是再新增一套顶栏。
- 该事项不构成当前产品能力缺口或发布门禁，只有出现明确的用户可发现性、无障碍或平台
  一致性问题时才恢复评审。

### 恢复实现时的边界

- 原生菜单只能作为现有 Command Registry 的适配入口，复用稳定 command ID、可用条件和
  快捷键 Resolver；不得在主进程复制保存、工作空间或设置等业务逻辑。
- 生产版不暴露“重新加载窗口”或“开发者工具”。
- 验收至少覆盖：菜单与快捷键执行结果一致；Markdown、Terminal 和内嵌浏览器的原生编辑
  动作作用于当前焦点；未登录或远程离线时本地菜单仍可用。

## Windows x64 安装包候选

状态：技术可行性较高，暂未进入当前路线图；先保留为 Windows 原生构建与真人验收候选，
不能把“生成 `.exe`”表述为 Windows 产品能力已经交付。

### 评估结论

- Electron Builder 可以生成 Windows NSIS 安装包，现有文件、Markdown、内嵌浏览器和多数
  工作台代码具备跨平台基础。
- Terminal 已有 `win32` shell、信号和浏览器启动器分支，`node-pty` 提供 Windows ConPTY
  支持；Android/ADB 已处理 `.exe`、`LOCALAPPDATA` 和 Windows SDK 路径。
- 当前正式打包配置、本地打包脚本、CI、Release 工作流和更新 Manifest 仍只覆盖 macOS
  arm64 DMG。因此短期可以产出内部测试包，但不能直接追加公开稳定 Windows Release。
- 首个目标只考虑 Windows 10/11 x64。Windows ARM64、应用内自动更新、Microsoft Store 和
  企业 MSI/MSIX 不与首个闭环捆绑。

### 用户端到端验收动作

只有在干净的 Windows 10/11 x64 环境完成以下动作后，才能把候选提升为 Windows Beta：

1. 用户下载并安装 NSIS `.exe`，首次启动无需 CCLink 登录或远程服务配置。
2. 用户打开本地目录，创建、编辑、保存 Markdown，重启后工作区和 Tab 正常恢复。
3. 用户打开内嵌浏览器并加载网页，再启动 Terminal 执行一条 `cmd` 或 PowerShell 命令。
4. 未安装 ADB、未登录 CCLink、远程服务离线时，本地工作台仍可使用且错误明确降级。
5. 安装 Windows 可用的 Claude Code 运行时后，用户能让本地 Agent 读取并修改一个工作区
   文件，权限拒绝和停止操作可用，Agent 故障不影响编辑器、浏览器和 Terminal。
6. 安装、升级或卸载不会删除用户工作区、普通设置、凭证或会话数据。

### 实现前必须关闭的缺口

- 在 Windows GitHub runner 原生安装依赖、构建和打包，避免把含 `node-pty` 原生依赖的
  macOS 交叉构建当作正式事实；为 Windows 增加独立的产物结构和启动 smoke。
- 把 Claude Code 自动发现从 Homebrew 路径和 `/bin/zsh` 扩展到 Windows，并为受管 Runtime
  增加经过哈希、版本和平台校验的 `win32-x64` 目录项；没有 Runtime 时 Agent 必须单独
  降级，不能阻止工作台启动。
- 真人核对 `hiddenInset` 标题栏、窗口关闭/最小化、拖拽区域、Cmd/Ctrl 提示、中文路径和
  长路径；不能只靠 renderer 单元测试判断 Windows 窗口可用。
- 验证 `%APPDATA%` 下明文凭证与 refresh token 文件的 Windows ACL、原子替换和诊断脱敏
  符合现有安全声明，不得引入 Windows Credential Manager、`safeStorage` 或第二凭证 Store。
- 公开发布前单独决定 Authenticode 签名、SmartScreen 预期、Release runner 权限和 Windows
  更新资产格式；继续由现有 `UpdateService` 与正式 Release 工作流统一拥有状态和发布事实，
  不引入第二 updater 或旁路上传流程。

### 建议恢复顺序与止损点

1. 先做 Windows x64 内部技术预览：原生 CI 生成 unsigned NSIS 包，只验证安装、启动、
   Markdown、浏览器和 Terminal。预估 1–2 个工作日。
2. 技术预览通过后再补本地 Agent、凭证权限、窗口体验和打包 smoke，形成可真人验收的
   Beta 候选。预估再增加 3–5 个工作日。
3. 只有 Beta 验收通过且确有 Windows 用户需求，才投入签名、公开发布和更新链；预计完整
   公开版本总投入约 1–2 周，签名主体审核等外部等待时间另计。
4. 若同一原生依赖或启动阻塞连续失败两次，先保留“便携/内部测试包”作为替代路径并重新
   评估投入，不为了证明 Electron 能出包而扩张发布主线。

## ACP Runtime：Codex 接入暂缓

状态：低优先级，退出当前开发主线；不继续真实 API Key 验收、发布准备或能力扩展。

### 已有结果

- Claude Code 仍是默认 Runtime 和 Agent 启动基线；ACP 只是空 Thread 首次发送前可选的平级
  Runtime。
- 已完成 Codex ACP 的最小工程实现，包括独立路径和 API Key、文本与工具事件、一次性权限、
  取消、Session 恢复及进程隔离。
- 固定的 `codex-acp@1.3.0` 协议探针、自动化测试、类型检查和生产构建曾通过。
- 尚未使用真实 Codex API Key 完成工作空间文件修改、权限拒绝、停止和重启续接，因此不能
  声明用户闭环完成。

### 暂缓决定

- 2026-08-17 用户判断该能力当前不重要，不值得继续占用产品主线。
- 现有受控实现和 ADR 暂时保留，避免无收益地删除已完成工作；它不构成近期产品承诺或发布
  门禁。
- 暂停期间不增加自动安装、Runtime Registry、Studio MCP、ChatGPT 登录、第二个 ACP Agent、
  远程 transport、图片或手动上下文压缩。
- 若现有 ACP 代码产生持续维护成本或阻塞其他主线，再单独评估冻结、隐藏入口或删除，不能
  顺手扩大重构范围。

### 以后恢复时先验证

1. 先确认一个 Claude Code 无法满足、且用户确实愿意使用 Codex 的具体场景。
2. 明确谁提供和承担真实 Codex API Key，并完成一次真实文本请求和工作空间文件修改。
3. 验证权限拒绝、运行中停止、App 重启续接和 ACP 故障不影响 Claude Code。
4. 只有上述闭环证明有价值后，才评审自动安装、Studio MCP 或第二个 ACP Agent。

## 角色配置：本轮会话交接

状态：角色 V1 研发候选已形成，后续以异机安装版真人验收为主；本节只记录会话交接，当前
产品与架构事实仍以
[`角色与会话配置`](./features/agent-role-configuration.md) 为准。

### 已确认的产品边界

- 角色与 AI 员工领域分离、产品组合：角色是可复用人格模板；AI 员工是引用角色、资源和
  能力并可持续分配工作的执行主体。AI 员工当前暂停开发，Studio 商业范围只保留远程部分。
- 角色只影响人格、分析视角和表达方式，不扩大工具、权限、资源或数据访问范围。
- 全部角色共用一个“角色配置”Tab，点击左侧角色列表只切换该 Tab 的查看目标。
- 内置角色只读；“编辑副本”会创建本地角色并直接进入编辑。本地角色支持新建、编辑公开
  Manifest、`SOUL.md` 和建议 Skill，并通过“保存为新版本”生成不可变版本。
- 会话引用固定的角色版本；应用到当前会话、新会话默认值和角色定义编辑是三种独立状态。

### 本轮关闭的问题

- 角色编辑草稿已接入 Tab dirty 状态。切换左侧角色或关闭角色配置 Tab 时提供“保存 / 放弃
  修改 / 取消”；保存失败或取消都会阻止离开，底层 `openTab` 也不会覆盖脏草稿。
- 新会话默认角色采用“阻止归档”策略：UI 与主进程共同拒绝归档，用户必须先选择其他默认
  角色，不自动取消默认。旧版本若遗留“默认且已归档”状态，启动时恢复该角色为未归档，
  保留原默认引用。
- 角色入口的可发现性已调整：内置角色不再只显示语义较弱的“复制为本地角色”，而是显示
  “编辑副本”并直接进入编辑器；本地角色入口明确为“编辑角色”。

### 已有工程证据与未完成验收

- 草稿保护、默认角色归档约束及旧状态修复完成后，完整 `pnpm verify` 曾通过：235 个测试
  文件、1360 项通过、2 项跳过，类型检查、Lint、边界检查和生产构建成功。
- “编辑副本”入口调整后，类型检查、Lint 及真实 Electron UI smoke 12/12 通过；smoke 已
  覆盖“内置角色 → 编辑副本 → 编辑器”“新建角色 → 创建”“我的角色 → 编辑角色 → 保存为
  新版本”。
- 未完成的产品证据仍是安装版异机真人验收：应用角色后连续发送、重启后再次发送、角色包
  跨机器导入运行，以及七个角色的真实行为差异。没有这些证据时只能称为研发候选。
- 未保存草稿当前只驻留运行内存；应用退出或崩溃后不会恢复草稿。若以后要支持恢复，应单独
  设计草稿持久化和清理生命周期，不能直接写进角色正式版本存储。

## 定时任务：特殊 Markdown 任务文档

状态：暂缓，不进入当前开发；现阶段继续使用单一的结构化定时任务编辑模式。

### 想法

把定时任务 Tab 设计成一种特殊的 Markdown 任务文档，而不是传统配置页：

- 任务名称和正文使用 Markdown 式编辑体验。
- 文档顶部展示执行时间、工作空间、绑定资源和结果处理等属性。
- 保存状态、本机启用状态、下次运行时间、revision 和运行历史为只读区域。
- 时间、资源和结果处理通过类型化控件修改，不能直接改写显示文本。
- Markdown 正文用于自由描述任务、执行要求和完成标准。
- 视觉上是一篇完整文档，技术上优先把固定区域放在 Tiptap 编辑器外，与正文拼成同一
  文档表面；不优先采用可被删除或改名的固定 Markdown 标题协议。

### 不变边界

- `ScheduledTaskService` 继续是任务定义、启用状态和运行事实的唯一状态所有者。
- Markdown 体验不能成为第二事实源，也不能绕过主进程的时间、路径、权限和工作空间
  校验。
- “是否在此设备启用”属于本机状态，不写入可复制的 Markdown 内容。
- 当前版本仍只承诺受限的工作空间读取和文本结果，不借 UI 改版扩大 Terminal、Browser
  或外部动作权限。

### 暂缓原因

- 当前立即引入会形成“配置页 + Markdown 文档”两套编辑模式，增加用户选择和状态同步
  成本。
- 尚未决定旧任务如何迁移、特殊文档如何导入导出，以及属性区与 Markdown 正文的保存
  边界。
- 在恢复该方案前，必须先确定单一事实源和端到端验收动作，避免出现表面文档已修改、
  调度器仍执行旧配置的分叉。

### 以后恢复时先验证

1. 新建任务只出现一种编辑体验，不要求用户选择“表单模式”或“Markdown 模式”。
2. 用户可以自由编辑正文，但不能直接改写工作空间、本机启用状态和运行历史。
3. 修改时间或资源后，保存产生新 revision，Tab dirty 状态与侧栏投影一致。
4. 复制正文不会复制本机启用状态；导入失败时不创建半有效任务。
5. 旧任务打开后内容、计划、资源和结果处理均无损，不产生第二份任务。
