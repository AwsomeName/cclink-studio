> 设计阶段交付。原型使用虚构的账号、稿件和平台 ID，配图是线描示意图，不是实拍；没有连接知乎，也没有改动业务代码。界面与产品逻辑确认后才进入实现。

## 一句话结论

运营要做四个决定：**用哪个账号、发哪一版、知乎上会呈现成什么样、只存草稿还是授权公开提交一次**。前三项都要能逐项核对，最后一项是两个互斥选项，默认都不选。点过提交后，Studio 只做只读核验：审核中可回原任务查看，没有回执时保留那一次提交记录，找到匹配的公开作品后才给出链接。所有进度只由 WebAffair 原任务写入。

## 主场景

运营刚收到审稿人标记“可发布”的 AI 眼镜试戴稿（修订 v3，3 张图、3 条图注），要投到公司的知乎号“样机实验室”。同一台 Studio 上还登记了第二个知乎号“研发手记”。也可以不经稿件生成，直接选工作空间里一份手写的 Markdown。

## 四个决定怎样画清楚

**用哪个账号。** 账号标签是公司起的名字，可能重名。真正的判断依据是知乎页面上的 `url_token`。核对在账号自己的 Profile 窗口完成，主进程只读读取。实际身份与登记身份不一致时，界面会显示读到的身份并阻止选择。修复方法是在该账号自己的窗口重新登录，Studio 不接触密码和验证码。选定后任务只属于该账号；执行时 `page.inspect` 还会再读一次，不一致就停止写入。历史上曾因选错 CSDN 账号产生一条中断任务（[第 197 天记录](../../../../testing/article-day197-2026-09-28.md)），所以这一步放在最前面。

**发哪一版。** 只能冻结已审版本。工作区文件在 v3 之后被改过时，界面会显示逐句差异。示例里的两处改动都超出了试装证据：“彻底解决了压痕问题”，以及把 4 小时改成 6 小时。这时只能改发 v3，或回到稿件生成重新审稿。手写 Markdown 没有审稿记录，由运营在这里逐项处理阻塞项，例如外链图和缺失图注，处理后另存修订。

**平台上实际怎样呈现。** 预览按知乎专栏样式模拟，并明确标注“以执行后从知乎回读的结果为准”。“正文与转换”页签列出每一项格式变化：标题行转为标题字段，小标题和列表保留，替代文字会被知乎丢弃，图下斜体行转为图片说明。“配图”页签逐张显示文件、前文位置、图注和规格，并可在预览中定位。“远端草稿”页签只列出该账号在创作中心里的草稿。标题不同的草稿不能选，以免覆盖别的文章；选用已有草稿时，会对比作者、标题、正文和图片数。

**只存草稿还是授权公开一次。** 两个选项互斥，默认都不选，开始按钮在选择前不可用。点击开始即构成本次有界授权，与快照一致的那一次提交不会在末尾再次确认（架构宪法第 7 条）。登录、验证码、安全验证、原创或版权声明、账号不一致以及无法判断后果的弹窗，都会停下交给人处理。只存草稿完成后，可以在同一原任务上追加公开授权：从“复核发布目标与有界授权”继续，不重传图片。

## 结果与恢复规则

| 结局 | 显示的事实 | 允许的操作 | 不允许 |
| --- | --- | --- | --- |
| 只存草稿 | 草稿 ID、知乎原稿 GET 回读一致、提交 0 次 | 在知乎打开草稿；追加公开授权一次 | 自动公开 |
| 审核中 | 提交 1 次及时间、回执 ID 与草稿一致、管理页状态原文“审核中”、最近观察时间与来源 | 只读复查；回原任务看执行计划 | 重发；没看见“审核中”时显示审核中 |
| 回执未知 | 提交记录（时间、代次、授权快照）保持 1 次 | 只读核验：按账号、文章 ID、标题加时间窗查找；多个候选由人认领，主进程按作者、全文和三图复核 | 重新提交；无命中就判定未送达；自动选最近一篇 |
| 已公开 | 作品链接；作者 url_token、标题、全文、三张图的地址、顺序、位置和加载；核验来源与时间。若是从“未知”找回，会写明来源 | 打开作品、复制链接、回原任务 | 只有链接、缺全文或缺图时显示“已公开” |

关闭窗口、重启或进入新的运行代次时，提交记录都会保留，也不会被新的授权抵消。推广首页的状态只是原任务的投影：来源不可用时显示最后核验时间，空列表不能当作“全部完成”。

## 状态所有权：沿用 WebAffair，不新增第二个 owner

| 界面元素 | 现在的事实来源 | 本设计要求 |
| --- | --- | --- |
| 账号、Profile、登录观察 | `WebResourceService` + 每个 Profile 的会话诊断 | “核对实际身份”复用按 `accountId` 打开可见 Tab 的现有入口，只读取 `url_token` 和显示名 |
| 授权范围 | `ArticlePublishingState.composer.allowPublish` + `platformAccountId` | 两个选项映射到 `allowPublish=false/true`。**拟增**：在同一 Affair 上把 false 改为 true 的受校验命令，不重建任务 |
| 原稿与冻结 | `source`（路径、mtime、size）、`assets`、`fields` | **拟增**：内容指纹与只读版本（沿用上级方案的同一建议），授权快照显示指纹 |
| 执行计划逐行状态 | `ZHIHU_ARTICLE_PUBLISHING_PLAN` 与 `articlePublishingDetailDefinitions` 的定义，结果由 WebAffair 按真实边界写入 checkpoint、current operation 和 transitions | 原型的逐行标题、执行者、进入和完成条件都取自现有定义。**拟增**两行：图注（知乎图片说明）回读；提交前读出发布设置的实际值 |
| 平台草稿 | `draft.platformDraftId`、`platformAccountId`、`recovery` | “远端草稿”页签只读展示这些字段，并在创作中心只读列出该账号的草稿 |
| 提交与结果 | `sideEffects`（publish 效果键）、`publication.status`：`dispatched` / `verifying` / `published` / `result-unknown` | 现有状态没有“审核中”。**拟增**：在原检查点加入结构化观察（平台状态原文、文章 ID、来源、时间），只用于显示，`publication.status` 继续保持 `result-unknown` 的保守语义 |

不新增 operation 账本、claim/report MCP、短 Run 调度或第二套 IPC。原型里的“推进 1 个事件”只是模拟 WebAffair 收到的真实事件；产品中界面不会按计时或 Agent 自述改变状态。

## 现状与拟增

已有能力（仓库代码及历史实测）：知乎适配器能在管理页找回原稿或新建独立草稿，按 `url_token` 核对作者，逐图上传并核验地址、次数、顺序、位置和加载（知乎不保留替代文字），核验正文 GET 回读和标题，以及一次提交后的公开页核验。第 197 天的正式任务在第 1 代完成，并核验了全文和三图。

本设计新增、待实现：

1. 发布入口的“刚审好的稿”置顶，以及“发哪一版”的差异与阻塞。
2. 账号页的“核对实际身份”按钮，以及同平台多账号并列展示。
3. 平台预览五个页签，其中“远端草稿”是只读列表和对比。
4. 授权页的两个互斥选项和快照；同一任务从只存草稿追加公开授权。
5. 执行计划中的图注回读、发布设置实际值两行；结果页结构化显示审核观察；回执未知的多候选认领。
6. 内容指纹（与上级方案共用）。

## 真人验收路径

在真实 Studio 上，使用两个真实知乎账号（A 为公司号，B 为另一个号）和一篇已获准公开的稿执行。没有负责人对“账号 A + 这篇稿”的公开授权时，只做到第 8 步。原型内同样内容见 [验收页](prototype.html#accept)（[截图](screens/15-accept.png)）。

1. 在稿件生成审稿后点“用这篇稿发布”：发布页顶部是这篇稿，版本 v3，3 张图、3 条图注；此时尚未打开任何浏览器。
2. 改选一份手写 Markdown（含 1 张外链图、1 处缺图注）：两项问题被逐条列出，“下一步”不可用；处理并保存为新修订后才能继续。任何问题被静默忽略即为失败。
3. 在账号 B 的窗口登录成另一个知乎号，再点 B 的“核对实际身份”：B 显示“身份不一致”和本次读到的 url_token，B 不可选，A 仍可选。B 被选中或自动改用 A 即为失败。
4. 选 A 进入平台预览，在工作区文件里改一句后回来：“发哪一版”出现未审改动差异，不能冻结；改回 v3 后可继续。
5. 依次打开五个页签：三张图位于原段落之后，图注逐条可见；字段表写明谁处理、怎么核验；草稿列表只列出 A 的草稿，标题不同的草稿不可选。
6. 在授权页先不选任何一项：开始按钮不可用，两个选项互斥。
7. 选“只存知乎草稿”并开始；在图 2 上传时关闭 Studio 窗口再打开：执行计划按真实事件逐行变化；重开后进入新的运行代次，图 2 显示“结果未知 → 等你确认”，确认前图 3 不开始。图 2 被直接重传，或计划显示全部完成，即为失败。
8. 草稿完成后，在知乎创作中心打开该草稿：标题、全文、三张图及其位置与预览一致；Studio 中提交次数为 0，提交和公开核验行显示“本次不执行”。
9. （获授权后）在结果页点“授权公开提交一次”：同一原任务从“提交前复核”继续，图片不重传，提交派发 1 次。
10. 已公开：结果页给出可打开的作品链接，作者为 A 的 url_token，全文和三图核验通过，来源与时间可见。只有链接、缺少全文或图片核验时，必须分别标出缺项。
11. 若知乎显示审核中：结果页写明管理页原文“审核中”与观察时间；推广首页该行显示相同状态，点该行回到同一任务；复查为只读。
12. 若点过提交却没有回执（可在提交后立即断网复现）：提交记录保持 1 次，只读核验可以重复执行，无命中时仍为“结果未知”；整个界面没有重发入口，重启后记录仍在。派发次数增加属于严重失败。

每次验收记录：Studio 版本、日期、脱敏任务 ID、账号 url_token 尾号、图数、派发次数、人工介入点与耗时，以及是否有开发者救场。“执行计划随真实事件变化”和“一次提交取得公开证据”分开判定；没有经历审核时，该分支标为“未实测”。

## 拷问：这份设计还没解决什么

- **图注无法自动核验。** 现有知乎适配器回读正文时会剔除 `figcaption`，所以“图注一致”目前没有证据。实现前，界面必须显示“图注未自动核验”，不能打勾。
- **“审核中”没有持久状态。** 第 197 天的头条任务就停在“管理页审核中、持久化仍为 result-unknown”。本设计要求增加结构化观察，但不新增状态；如果实现时为了显示方便改动 `publication.status`，就违反了保守语义。
- **知乎字段的真实约束未核实。** 标题长度、专栏、话题、可见范围的实际限制和默认值，本次没有在真实页面读过。字段表只承诺“标题写入并回读，其余读出实际值”，不承诺能设置。
- **“核对实际身份”需要打开一个可见 Tab。** 这会在当前工作空间产生一个浏览器 Tab，且需要该账号已登录。是否在核对后自动关闭、是否允许后台核对，需要实现时按 BrowserManager 生命周期决定；不能为此新建第二种 Tab。
- **追加公开授权是新增命令。** 它改变了已有 Affair 的授权范围，必须经主进程校验：同账号、同冻结版本、无未知副作用，并重新记录授权时间。范围变化不能静默发生。
- **原型的执行事件是模拟的。** 真实执行计划能否像原型一样逐行变化，只能在真实应用中验收，见第 7 步。
- **用户功能进度：** 本轮没有新增用户可用能力，只交付了设计、可点击原型和验收路径。用户现在已经能用现有 Studio 选择 Markdown 发知乎并核验公开结果，这是历史实测的结论，本轮没有复验；上面 1–6 项新增能力都还不能用。
