## 一句话

Owner 判断“照约定的来源查不完必需结果”时，不再记成“运行出错”、只给一个原样重跑的按钮，而是逐项列出哪些结果已有证据、缺什么、为什么现有来源补不上，再让你在三条路里选一条：**扩大来源**、**先交付已核实部分**、**改目标**。

- 约定确认后无法修改：要加公开网页或换来源，只能新建一件事务，已核实的 13 份原文也得重新取证。

## 规则

1. **区分两种停下**：`blocked`（Owner 判断来源不够）进入“待你决定”；技术故障仍是“运行出错”。来源不够时不提供原样重跑。
2. **Owner 必须给结构化判断**：`blocked` 要逐项写明每个约定结果的状态和依据，列出缺口及原因，并可附一个来源修订建议（加公开网页、加 GitHub 仓库、加本地目录）。缺这些字段时退回 Owner 重写，不能只给一段话。
3. **修订是新的授权**：新增的来源要经你确认才生效，Owner 的建议本身不算授权。公开网页要写明上限和“搜索词和网址会发给 DeepSeek”。修订只能增加来源或调整结果，不能悄悄把必需结果改成可选；改成可选只能走“改目标”，并由你确认。
4. **已核实的保持有效**：原文、引文定位、各执行会话的核对结论都不重做。修订后 Owner 只针对缺口派工。
5. **部分交付不算完成**：“已交付 · 有缺口”在列表里单独显示，简报开头必须列出未完成的结果。引文仍按现有规则逐条核对，核对不过照样拦下。
6. **轮次用完的情况**：如果是派工轮次用完（Owner 还想继续查），同样进入“待你决定”，但多一个“按原来源再查一轮”，因为再查可能取得新证据。

## 状态与存储

- 状态所有者仍是事务记录（Research）。新增 `block`：停下原因、逐项结果状态、缺口、来源修订建议、时间；`phase` 用 `decide`，和“跳过的步骤待你决定”共用列表分组。
- 约定修订写入 `事务配置.md` 的修订历史（时间、增加的来源、调整的结果、谁确认），`工作记录.md` 记一条事件。确认后的约定照旧由主进程的事务目录写入，渲染进程不另存一份。
- 部分交付：报告新增 `gaps`（未完成的约定结果及原因），交付文件名不变，补齐时写新版本。
- 规划阶段已经收紧（`b5137435`）：必需结果依赖仓库以外的资料时，Owner 要开联网或明说做不到。这个设计处理的是规划已经确认、取证中途才发现来源不够的情况。
